# Switches

Reference for the console variables and startup flags behind the [performance work](PERFORMANCE.md).

Every performance change has a switch that brings back the original path, and both paths give the same sim checksums. So does every ported FAF FA-Binary-Patches change a player can notice (rows that name a patch number). Console variables can be set in game (`name value` in the console) or at startup with `/con name=value;name2=value2`, which runs on the first frame. "Live" means a change applies from the next use; "next game" means the value is read when a thread or session starts.

## Frame clock in network sessions

`wld_FrameClockNetwork` is off by default because a session with a retail client gets no reliable gain from it, and our client gets choppier.

The game clock decides when the UI takes finished ticks off the sim's queue. In a network session this also sets when the client tells the others to advance, and a tick only runs once every client has done so. Retail's clock is the median of the last 10 frame times. When one frame per tick is long and the rest are short, the median is a short frame and the game runs below its set speed, even though the sim keeps up. The mean adds up to real time, but it can't make a retail client on the median go faster.

Measured on 2026-11-02 with `mpemu`: 2 players on one machine, normal game speed, a 1000 v 1000 air fight on a test map. "Median" is today's behaviour, "mean" is `wld_FrameClockNetwork 1`. In the retail rows, retail stays on the median and only our client changes.

Ticks per second over game ticks 300-900, where 10 is normal speed:

| Players | Network | Games per clock | Median | Mean |
|---|---|---|---|---|
| Ours + ours | No lag | 3 | 9.19 | 9.98 |
| Ours + ours | 50 ms latency, 10 ms jitter, 1% loss | 2 | 9.28 | 9.99 |
| Retail + ours | No lag | 3 | 8.28 | 8.58 |
| Retail + ours | 50 ms latency, 10 ms jitter, 1% loss | 2 | 8.62 | 8.41 |

Smoothness on our clients over the first 300 s of the lag games:

| Players | Measure | Median | Mean |
|---|---|---|---|
| Ours + ours | Frames with no tick ready | 2.0% | 1.2% |
| Ours + ours | Spread of the time between shown ticks | 22 ms | 16 ms |
| Retail + ours | Frames with no tick ready | 11.9% | 21.5% |
| Retail + ours | Spread of the time between shown ticks | 33 ms | 41 ms |

None of the 24 games played desynced or crashed. Four no-lag retail games aren't in the tables: retail stalled in them, on both clocks, for a reason not found. The tests didn't cover separate machines, more than 2 players or our x86 build, and the choppiness wasn't judged on screen. The mean clock doesn't change what the sim computes, and in these games it didn't take a game above its set speed.

## FAF game version

FAF ships its engine fixes ([FA-Binary-Patches](https://github.com/FAForever/FA-Binary-Patches)) as a new exe with a game release, and the FAF client stamps the game version into that exe, so one game version means one set of engine patches. This engine carries those patches up to game version 3840 and applies them per session: a replay plays with the patches of the version in its header (`Supreme Commander v1.50.<version>`, accepted from 3835 to 3840), and every other session with those of the game data in use, `Version` in `/lua/version.lua` (FAF's `GetVersion()`). The FAF client gives every player of a game the same game data, with the exe of that version, so a game with players on the FAF exe needs no setting; data without that file counts as 3835. The replay a session records names the version it ran as. The log says `FAF game version <n> (replay|game data|sim_FafGameVersion), sim fixes 0x..` when a session begins. `GetEngineVersion` reports 1.5.3840, the newest version whose patches the engine carries.

The switches below are read when a session begins. In a multiplayer game every client must use the same values, so leave them at their defaults there; they are for replays and tests.

| `sim_FixAimLeadOncePerTick` | −1 | `/con` | next game | FA-Binary-Patches #143 (from 3836): no one-tick velocity lead on a target that already moved this tick; −1 follows the game version, 0 off, 1 on |

## Server mode

Server-authoritative sessions are being built: one server runs the only sim, and each player receives only what their army can see. The code is behind the CMake option `FAF_SERVER_MODE` (off by default; the presets `clang-x64-release-server` and `clang-x86-release-server` turn it on). A client built with it is the same lockstep client for every normal game, replay and lobby: the server-mode path runs only when `/connectserver` is on the command line, and it never falls back to a lockstep session. The test switches `/loopback` and `/sessionsummary` below change nothing unless given.

## headless

The engine builds three programs: `main` (the game client: `main_x64.exe`, or `main.exe` on x86), `headless` (below) and, later, `server`, the dedicated game server.

Every build also produces `headless_x64.exe` (`headless.exe` on x86; `headless` on Linux), a console program that plays one replay with no window, render device or audio engine and reports whether every checksum the players recorded matches. It runs the game's sim, sim driver and replay client; it does not build the world session the game's UI runs on. Put it in a folder of its own next to the game's `bin` folder (it reads `../Installed.Prefs` and mounts the `fafengine` folder next to itself, as the game does) and give it the game's init file:

```
headless_x64.exe --replay C:\full\path\26902315.scfareplay /init C:\ProgramData\FAForever\bin_x64\init.lua /nosound /log replay.log
```

headless links only the simulation's objects: no UI, graphics or audio code and no wx, Direct3D, D3DX, XACT, DirectSound or FFmpeg (its matrix helpers are `gpg/gal/MatrixPortable.cpp`, its maps load into the headless terrain resource, and it decodes sync data into a Lua state of its own instead of the user state). It opens no window and no message box: an engine message box (`WIN_OkBox`) prints its text to stderr. Because every build links it, a simulation change that calls into UI, graphics or audio code fails the build there: the link fails on the missing library, and after every link `cmake/HeadlessImports.cmake` fails the build when headless imports any DLL besides KERNEL32, ADVAPI32, ole32 (starting COM only), SHELL32, SHLWAPI, WS2_32 and dbghelp. Debug builds keep every function they link, so they catch what a release build's dead-code elimination would hide. `--wire-stats`, `--loopback`, `--command-check` and `--oracle-check` use the wire format and the remote client (`src/remote`), which only a server-mode build has (`FAF_SERVER_MODE`, the `*-server` presets); elsewhere they are refused with exit code 4. Whether that terrain resource reads maps as the client's does is checked by the test program `faf_terrain_check` (`tests/terrain`, not built by default): `faf_terrain_check --maps <list> /init <init.lua>`, from a folder staged like headless's, loads every `.scmap` named in `list` (one path per line) with both and compares where the terrain data ends in the file, the heightfield, the terrain-type grid, the water settings and the props. It prints one `TERRAINCHECK same` or `TERRAINCHECK DIFF <what>` line per map and `TERRAINCHECK maps= differences=`; exit 0 when nothing differs.

**Profile-guided Linux build.** The `linux-clang-x64-release` preset, which the Replay check and Replay parity workflows build, optimises with counts recorded from real games: `cmake/pgo/headless-linux-x64.profdata`, with ThinLTO. It needs `llvm-18` for `llvm-ar`. `linux-clang-x64-release-plain` builds without it, for comparing. The Windows builds and the game don't use it: a profile only fits the platform it was recorded on.

Counted by the CPU on one thread against the plain preset, both builds running at once, with the stored profile (recorded from 26885749, 26935800, 26902315 and 26901494): instructions -16.6 %, cycles -12.8 %, time -10.9 % on 26885749, a game it was recorded from; instructions -10.6 %, cycles -9.7 %, time -7.4 % on 26943656, a game it was not. The same bytes on every beat of both, and no mismatch on 9 further replays.

Changed code keeps working with an older profile: a function that changed is compiled as if unprofiled, so the gain fades slowly and nothing breaks. Code no recorded game runs is treated as cold, so a new hot path gains nothing until the profile is recorded again. To record: `tools/pgo/record.sh --init <init_replay.lua> <replay files>` (needs `libclang-rt-18-dev` as well), then compare with the plain preset, both builds running at once.

The last line it prints is `VERDICT ended=<True|False> mismatches=<n> crash=<True|False>`, the same verdict `tools/runs/replay_20261013/run_replay.py` prints for the game. `ended` is the sim's Lua `Sync.GameEnded`, which the game reports to FAF; the run itself stops at the sim's game-over beat (a victory, or the end of the recorded commands).

A client that joined builds its launch from tables it rebuilt from the host's config bytes, which is what the check does with the host's header, so host header against joiner header compares like with like (the scenario info then matches byte for byte). `FAF_LAUNCHCHECK_VERBOSE=1` prints, for each value that differs only in key order, both key orders around the first difference |
| `--disk-trace file` | — | Writes one line for every file the engine finds (`stat`), opens (`open`), reads (`read`) or maps (`map`), with its full path inside the archive or folder it came from, and for every directory listing: `list <prefix> <pattern>` (` recursive` when it searches subfolders) or `children <prefix>`, followed by each mounted path it returned (`listed` / `child`). Only files that exist are written. From the first mount to the verdict, so the file lists the game data a run needs; the CI parity data pack is cut down to it |
| `--path-spelling file` | — | Linux only. Writes one line, `asked<TAB>on disk`, for each path the shim found on disk only by ignoring case (each pair once). Windows finds such a path without changing it, so an empty file means case played no part on this run (dedicated-server plan WPR.23). |
| `--checksum-period n` | the game's (50) | `sim_ChecksumPeriod` for this run. With 1 every beat has a digest. Other code feeds the checksum between checksum beats, so a period other than the recorded 50 digests different spans of data: the verdict then says "recorded-checksum check skipped" and mismatches do not count. The period changes only the checksum, never the sim (plan §12, 2026-10-25) |
| `--state-digests file` | — | Writes `beat digest` of what the sim published each beat (creations, entity and unit updates, deletions, army economy, the Lua `Sync` bytes). Independent of `sim_ChecksumPeriod` and of the sim's checksum, so runs with different periods can be compared |
| `--lead n` | 10 | Beats the sim may compute ahead (`sim_ReplayLead`); headless issues beats without the rate clock (`sim_LeadOnSchedule 0`), so the sim runs flat out |
| `--timeout minutes` | 180 | Gives up after this long |
| `--label text` | `headless` | Prefix of every printed line |

Engine switches work as in the game: `/init`, `/log`, `/synclog`, `/simworkers`, `/con`, `/prefs`, `/sse2`, `/noversioncheck`. Exit code: 0 every recorded checksum matched and the replay reached its end; 1 a mismatch; 2 the end was not reached in time; 3 a crash or fatal error; 4 bad arguments or a replay that could not be loaded.

## Desync recorder

Issue #216. A desync writes `desync_<FAF game id>_beat<N>_army<A>.zip` into the folder of the `/log` file, so next to the game's log (the working folder without `/log`), once the sim reaches the mismatched beat + 30, the same beat on every client so their state snapshots line up (at least 10 beats after the mismatch was seen). Nothing goes to disk before that. Checksums are the same in every mode. The recorder has two modes:

- **Hashed state** (`sim_DesyncDump`, on by default in live multiplayer games, off in replays and single player): each beat, `Sim::UpdateChecksum` also copies the values it hashes (every army's economy, every moved entity's id, health, blueprint, position, rotation and velocity, the random generator's state) into a memory ring as bytes, nothing formatted. On a desync, the recorder's own thread turns the kept beats into the dump's beat logs, each value with its float bits. No call trace (which unit ran which command). It costs no measurable sim time: the same two heavy vault replays took 351 s and 344 s, 480 s and 481 s, off and on (`/desyncdump`, `/simworkers 4`).
- **Full sync log** (`sim_DesyncRecorder`, off by default): the `/synclog` text of recent beats, compressed in memory, call trace included. It formats text for every hashed value and every traced call each beat, which costs sim time: two heavy vault replays took 9 % and 16 % longer with it on (365 s against 398 s, 474 s against 551 s, `/simworkers 4`). It replaces the hashed-state mode when both are on.

At game start the log names the folder: `Desync recorder: hashed state of recent beats in memory (sim_DesyncDump, live multiplayer game), cap 32 MB; a desync writes its dump to <folder>` (or `Desync recorder: on (sim_DesyncRecorder 1), ...`); after a desync, `Desync recorder: wrote <path> (<bytes> bytes)`.

| Switch | Default | At startup | Applies | What it does |
|---|---|---|---|---|
| `sim_DesyncDump` | -1 | `/desyncdump` (1), `/nodesyncdump` (0) or `/con` | next game | Keeps the hashed state of recent beats in memory for a desync dump. -1 in live multiplayer games only, 0 never, 1 always (replays and single player too) |
| `sim_DesyncRecorder` | 0 | `/desyncrecorder` (1), `/nodesyncrecorder` (0) or `/con` | next game | Records the full sync log of recent beats for a desync dump; recording stops once the dump is taken. 0 never, 1 always, -1 in live multiplayer games only |
| `sim_DesyncRecorderMB` | 32 | `/con` | live | Memory cap for the kept beats, in either mode; the oldest go first. The beats kept reach back to the last beat every player's checksum agreed on, at most 192 (one checksum period, 128 beats of report delay and the beats recorded after a mismatch is seen) |
| `sim_DesyncTestNudgeBeat` | -1 | `/desynctestbeat N` or `/con` | live | Test only: on the first checksum beat at or after N, this client alone raises its lowest-id moving unit's health by one float step, so the game desyncs for real |
| `sim_DesyncDumpBeat` | -1 | `/desyncdumpbeat N` or `/con` | next game | Writes the dump when the sim reaches beat N, mismatch or not, keeping the newest beats whatever the checksums say. For rebuilding the side of a desync nobody sent from a replay (`tools/desync-diff/`). -1 waits for a mismatch |

Compare dumps with `tools/desync-diff/desync_diff.py` (issue #217); it prints the first value that differs.

## Desync telemetry

Issues #218 and #219. On by default, to the faf-re desync server (`fafre-metrics.draiget.dev`, behind Cloudflare); `/notelemetry` turns it off. Setting up a collector and dump receiver of your own: [Desync diagnostics](DESYNC_DIAGNOSTICS.md). A live multiplayer game sends two kinds of OpenTelemetry log record, as one OTLP/HTTP JSON `POST` each to `<telemetry_Endpoint>/v1/logs`:

- `faf.desync`: one per player whose hash differed from ours at the first mismatched beat, sent when the sim reaches the dump beat (the mismatched beat + 30, as for the recorder), so every player's report for that beat has arrived. Later desyncs only raise `faf.desync.later_records` in the game-end record.
- `faf.game.end`: one per game, desync or not, when the game's sim is destroyed (quitting, or leaving to the menu).

Every request carries the process: `service.name` `faf-engine`, `service.version` the commit (#215), `faf.engine.version` (`git describe`), `faf.engine.dirty`, `host.arch`, `faf.arch`, `os.type`, `os.description`, `faf.cpu.logical_count`. Both records carry `faf.game.id` (from `/savereplay gpgnet://host:port/<id>/...`), `faf.game.version`, `faf.sim_fixes`, `faf.map` (the map's folder name), `faf.game.mods_md5` (MD5 of the game's mod list, as the dump header's `game_mods_md5`), `faf.checksum_period`, `faf.players`, `faf.army.local`, `faf.sim.workers`, `faf.sse2`, `faf.switches.hash` (MD5 of every `sim_*` and `lua_Parallel*` switch value) and `faf.switches` (every reported number or on/off switch with its value, `name=value;...`), `faf.switches.changed` (each reported number or on/off switch whose value differs from what it was before the command line's flags and `/con` ran, `;`-separated; `sim_Workers` is left out, `faf.sim.workers` carries it). Reported switches are every `sim_*` and `lua_*` one and every switch this file's tables list, whatever its area: the build reads the names from this file (`cmake/FafBuildInfo.cmake`), so a new switch documented here is reported too. The dump header's `settings.switches` lists every reported switch, text ones too; `telemetry_*` is never listed. `faf.desync` adds `faf.desync.beat`, `faf.desync.last_agreed_beat`, `faf.desync.delay_beats`, `faf.game.time_s`, `faf.hash.local`, `faf.hash.remote`, `faf.army.remote`, `faf.source.remote`, `faf.desync.players_disagreeing`, `faf.desync.players_reported`, `faf.orders_altered`, `faf.fpu.x87_control`, `faf.fpu.mxcsr`, and `faf.dump.file` and `faf.dump.bytes` when the recorder wrote a dump, and `faf.dump.upload` (the uploaded copy's name) and `faf.dump.url` (`<telemetry_DumpEndpoint>/<game id>/<name>`, where `receive.py` serves it) when it is uploaded. `faf.game.end` adds `faf.game.beats`, `faf.desync`, `faf.desync.beat` and `faf.desync.later_records`. The records never carry player names, FAF user ids, the command line, file paths or dump contents.

Dump upload: with `telemetry_DumpEndpoint` set and a dump written (by default in live multiplayer), the recorder also writes its dump's files as `desync_<id>_<beat tag>_army<A>.tar.gz` next to the zip, and the sender POSTs it to that URL as given (`Content-Type: application/gzip`, `X-FAF-Dump: <file name>`, the token as for records). The upload goes through the same outbox as a record, with six attempts instead of three (so a receiver that is down during the game gets up to four more starts) and a 30 s send and answer timeout; the `.tar.gz` is deleted once it is sent or dropped, and the zip stays. Unlike the records, a dump holds player names, the sync log and the command line. In both the zip and the copy, the token reads `<token>` and the user's folder in `\Users\<name>\` and `/home/<name>/` paths reads `<user>`. `tools/desync-diff/receive.py` is a reference receiver: it stores each upload under `<out>/<game id>/` and runs `desync_diff.py` (which reads `.tar.gz` dumps as well as zips) once a game has dumps from two armies.

Sending runs on its own thread; the sim and render threads only queue a record. Each record goes to an outbox file next to the game log (`faf_telemetry_outbox_<pid>.txt`) before it is posted and leaves it once the collector answers 2xx. A failed record is retried with the next record (the game end) and at the next start, three attempts in all; a starting client also sends the outbox files of clients that no longer run, never those of a client still running in the same folder; a 4xx answer other than 408 or 429 drops it at once. Requests time out after 3 s; when a game ends, the engine waits up to 4 s for the queued records before it goes on, so the game-end record is posted before a quit. Windows uses WinHTTP (http and https), loaded when the first record is posted; the Linux build posts plain http only. With telemetry on and neither recorder mode on, the recorder keeps checksums only.

| Switch | Default | At startup | Applies | What it does |
|---|---|---|---|---|
| `telemetry_Enabled` | 1 | `/notelemetry`, `/telemetry` or `/con` | next record | Sends the records (live multiplayer games only). Nothing starts while it is off: no thread, no file, no connection. `/telemetry` wins over `/notelemetry` |
| `telemetry_Endpoint` | `https://fafre-metrics.draiget.dev` (Linux: `http://`) | `/telemetryendpoint URL` or `/con` | next record | Collector base URL, `http://host:port` or `https://host`; `/v1/logs` is appended unless the path ends with it. Empty sends nothing |
| `telemetry_Token` | the desync server's upload token | `/telemetrytoken T` or `/con` | next record | Sent as `Authorization: Bearer T`. It ships with the game, so it only keeps casual junk out; reading what arrived needs the server's read token |
| `telemetry_DumpEndpoint` | `https://fafre-metrics.draiget.dev/dumps` (Linux: `http://`) | `/telemetrydumpendpoint URL` or `/con` | next dump | Where the recorder's dump is POSTed as `.tar.gz`, `http://host:port/path` or `https://host/path`, used as given. Needs `telemetry_Enabled`, `telemetry_Endpoint` and a dump; empty uploads nothing |

`/exitattick N` (test only) quits the game at game tick N the way `/exitongameover` does, so scenarios end their games cleanly: `tools/scenarios/2p-desync-telemetry.yaml`, `2p-telemetry-no-desync.yaml` and `2p-desync-dump-upload.yaml`.

## Debugging aids

Off by default.

- `FAF_LUAGC_TIMING=1` (environment) logs the phases of every sim Lua collection.
- `lua_GcVerify` (console variable, `/con lua_GcVerify=1`): every parallel sim collection is checked against a serial mark and sweep. It compares mark bytes and weak-table lists after both propagations and the sweep's live/dead classification. After the mark it checks that no marked weak table refers to an unmarked object, that no live closure keeps an open upvalue into a dead thread, and that the LuaObject root list is intact. Findings are `[GCVERIFY]` warnings, and every 100th clean collection logs `[GCVERIFY-OK]`. It roughly doubles collector time and stretches each sim mark, which also widens the window for races between the sim and other threads.
- `FAF_DUMP_ON_SIM_LUA_ERROR=<n>` (environment): the first n sim Lua script errors each write a full-memory minidump and the error text beside the exe (`faf_luaerr_*.dmp/.txt`), then the game continues. `FAF_DUMP_ON_SIM_LUA_ERROR_IGNORE` lists `;`-separated substrings of errors to skip, for errors a replay always logs (benchmark replay: `SetSpinDown;Failed to attach entity`).
