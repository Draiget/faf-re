# Map editor

`FafEditor_x64.exe` (x64) / `FafEditor.exe` (x86) is the map editor: its own program, built from the same engine code as the game. It draws through Direct3D 12 or Vulkan only, and plays maps inside its own window.

*Snapshot: 10/11/2026. Opening maps (from the game's folders, any folder, or the FAF vault), the 3D edit view, the terrain, texture, water, prop, decal, marker and unit tools, saving and packaging, Check, and Play inside the editor.*

## Building and running

```powershell
.\build.ps1 -Editor        # builds only the editor's target, copies FafEditor_x64.exe (+ .pdb) to bin_x64
.\build.ps1 -Editor -Configuration Debug
cd C:\ProgramData\FAForever\bin_x64
.\FafEditor_x64.exe /init init_faf.lua /log C:\ProgramData\FAForever\logs\FafEditor_x64.log
```

In VS Code, the Run view has "Editor (x64, Debug)" and "Editor (x64, Release)": F5 builds the editor's target of `clang-x64-debug` or `clang-x64-release`, copies it to `bin_x64` and starts it under the debugger with `/init init_local_development.lua` (the Lua of the FA checkout, as the engine's own F5 entries use). "Editor (x64, no build)" starts what is already there. Only running editors are stopped before the copy; the game is left alone. The `.vscode` files are local (not in git).

`-Editor` never replaces the game's `main_x64.exe`, its headless or the DXC DLLs in the run folder (the editor carries its own DXC); a Profile build is copied as `FafEditor_x64_profile.exe`, and `-Out` also copies it to `out\<arch>\`. The editor reads the game data the way the game does: `/init <file>` names the init file (FAF's `init_faf.lua`), else `SupComDataPath.lua` next to the exe.

**Mission** (Alt+6; `tools/EdMission.cpp`, `ui/EdMissionPanel.cpp`; a port of FAF Studio's mission compiler, C++ in place of its Lua, which needs Studio's own modules): Stages on the left of the Mission workspace, Strings, Bases and Platoons under it, Run in the bottom dock.
- A mission is stages; each runs its "When it starts" nodes, then its "Then" nodes. The objectives of a stage are one group whose completion starts the next stage (the last one ends the operation with a win unless it has an End node); a stage without objectives starts the next one at once unless it has a failsafe timer, an End or a Start next stage node; a failsafe timer starts the next stage after that many seconds whatever the objectives.
- 47 node types with Studio's settings: spawn a group (per difficulty, as wreckage), platoons and patrols, mission text and dialogues, waits, restrictions, resources, the playable area, revealing, alliances, destroying or giving groups, flags, transport drops, taunts, nuke barrages, five coop nodes, bases, a group spawned as a platoon (with a template and an order queue), an order queue given to a platoon, a platoon builder stopped, Raw Lua, End, Start next stage; triggers (timer, group destroyed, unit killed, units in an area, objective decided; each quiet once its stage has moved on unless told otherwise); if difficulty, if players, cutscenes with cameras; objectives (destroy, protect, survive, units in an area). Containers hold their nodes as a tree.
- Stages: the mode (campaign, coop, both), the stages (add, move, remove; name, failsafe), the two node lists, Add a node (inside the selected container, after the selected node, or at the end of Then), Up, Down, remove, and the selected node's settings: the map's armies, unit groups of the chosen army, chains, areas, markers and dialogues to pick from, numbers, switches, text (Raw Lua in a box). Its findings under the list. Strings: the dialogues and their lines (speaker, text, seconds). Every change is an undo step ("mission"); typing in a field is one when the field is left.
- What a mapper types reaches the script only quoted, as a finite number, as an identifier (a variable name that isn't one becomes V.UNSET), or as one category expression of a fixed alphabet; values out of range fall back to the defaults. Raw Lua is the escape hatch: a node whose code doesn't compile is left out with a WARN.
- Save compiles the mission into `_script.lua` between `-- >>> EDITOR MISSION v1` and `-- <<< EDITOR MISSION` with a hash: the region is replaced on each Save, a region edited by hand is left alone (the check says so), the editor's own empty script is replaced whole, a script with its own OnPopulate / OnStart gets only the stages and EditorMissionStart (to call from its OnStart). Every stage is checked to compile in the editor's Lua; a stage that still doesn't becomes one that starts the next and says why in the log. The mission itself is kept beside the map in `<map>_mission.editor` (JSON). A play of unsaved edits gets the test run's flavour: every node logs `EDMISSION trace <stage>.<section>.<node>` as the game reaches it.
- The check (Problems) adds the mission's findings: an empty stage, an unknown node, values that had to be replaced, a missing army / group / chain / area / marker / dialogue, a variable read before any node sets it, a coop node in a campaign, Start next stage in the last stage, a failsafe without a next stage, a mission that never ends, an empty dialogue, a category that isn't one expression; and whether the script with the mission compiles.
- A test vault map with two stages (`/missiontest`): the script compiled (2,573 bytes), the check said the mission never ends, the play traced stage.1, 1.enter.1, 1.enter.2, stage.2, 2.enter.1 in order; undo took the mission back.
- Run (the bottom dock, beside Problems): a test play's progress, kept from the log's `EDMISSION trace` lines: the stage it is in, every node it reached ("1 start: Mission text"), a trigger that fired, one dropped because its stage had moved on (amber); a click selects that node in Stages. Play from this stage starts the open map's test run at the chosen stage (the copy's EditorMissionStart calls that stage). A map with a mission always plays from a copy (also without unsaved edits), so its test run traces. A play from stage 2 (`/missiontest`): stage.2, 2.enter.1, nothing of stage 1.
- Bases (Studio's mbase): a BaseManager on an AI army, started by a Start a base node. Its army, marker and radius; its build groups (the army's unit groups, or their `_D1`..`_D3` versions with Groups per difficulty) and their priorities; spawned whole or Starts empty (its engineers build it); engineers and assisting engineers per difficulty, how many build at once, support ACUs, always assist; switches turned on or off and what it never builds. Its attacks (OpAI): the kind (land, air, naval, engineers), the platoon kinds and how many units per difficulty, the orders (a patrol chain picked per platoon, one chain, a random patrol, or the default), priority, a lock (after deaths, after building, a share lost), and up to two build conditions (humans have so many units, a flag is set, a stage reached). Compiled before the stages; an army that isn't in the game (a skirmish test play) only warns and the stage goes on. Checks: names, the army, the marker, the groups (per difficulty too), a base no stage starts, an attack without a chain or with an unknown one, names used twice.
- Platoons: platoon templates (the save file's `Platoons` layout: name, AI plan, a row per unit type with least, most, squad and formation; From a group makes one from a group's units) registered in `Scenario.Platoons` when the script loads, and order queues (Move, Patrol, Attack along a chain or to a marker, Stop; compiled to ScenarioFramework's platoon calls). Platoon builders are read from the army's `PlatoonBuilders` for Stop a platoon builder; they aren't edited here. Checks: names, empty templates, rows without a unit or with most below least, orders without a target, unknown chains, markers, templates, queues and builders.
- `/missiontest` also makes a base on the second army (the play: "army ARMY_2 is not in this game", then the next node ran) and a template (the play read 4 entries of `Scenario.Platoons['PLATOON_Test']`).
- Not here: importing a hand-written mission into stages; editing platoon builders (PlatoonBuilders) and the unit tree's own platoon / orders fields.

**Mod projects** (Alt+8 Units, the Mod project panel beside Properties; `doc/EdModProject.cpp`, `ui/EdModPanel.cpp`; after FAF Studio's mod projects):
- A project is a folder in the vault's `mods` folder (the test vault's with `/vault`), so the game lists it as a mod: `mod_info.lua` (generated; its uid is made once and kept), `editor_project.json` (the changes, so the project reopens; the copy before each write is kept as `.bak` and opened when the file can't be read) and one merge blueprint per changed unit, `units/<id>/<id>_unit.bp`, with only its changes and `Merge = true`.
- FAF merges a merge blueprint into the game's one table by table (`lua/system/Blueprints.lua` StoreBlueprint, `table.merged`) and has nothing that finds a weapon by its label, so a weapon change (kept as `Weapon:<Label>.<Field>`) is written by the weapon's place in the unit's `Weapon` list, looked up from the label when the project is written. A change whose weapon the unit doesn't have is left out and reported.
- Write leaves a file that doesn't compile in the editor's Lua, or one the project didn't write (no generated first line), as it is and lists it; the merge blueprint of a unit without changes any more is removed.
- The panel: the projects to open, New project, name, author, description, version, the uid, the changes (unit, field, value; a bin puts one back to the game's value), Undo / Redo of the project's steps and Write project.
- `/modtest` on the test vault: a project EditorModTest, daa0206 changed (mass 230 to 240, its Suicide weapon's damage 50 to 100): 3 files written, no problems; the merge blueprint holds `Economy = { BuildCostMass = 240 }` and `Weapon = { [1] = { Damage = 100 } }`; reopened with the same uid.
- **Unit lab** (Units, left, before Tools; `tools/EdUnitLab.cpp`, `ui/EdUnitLabPanel.cpp`): pick a unit (typed words narrow the list; changed units marked); its fields from the game's blueprint as the engine holds it: mass and energy cost, build time and rate, storage, health, regeneration, shield diameter, top speed, acceleration, braking, turn rate, vision / water vision / radar / sonar / omni radius, and per labelled weapon damage, damage radius, range, minimum range, rate of fire, muzzle velocity. A field shows when the unit has a value for it; the slider runs from 0 to four times the game's value (at least 10), a changed one is marked `~`, its arrow puts it back. Shield health and regeneration, production and upkeep live only in FAF's Lua tables and aren't offered.
- Every change is a step of the project's own history (Undo / Redo in the lab and in Mod project; a drag is one step; another project clears it): a mod project stays open across maps, so its steps aren't in a map's undo.
- Test: the project written, its folder mounted as `/mods/<name>`, the game's mods listed again (FAF's `mods.lua` cache cleared so a new project is found), the project switched on for the play (after the map's remembered setup is put in place) and the open map played.
- `/unitlabtest`: uel0201 (Medium Tank) mass 56 to 81, MainGun damage 24 to 72, undo and redo back to the same; Test played with "Active mods in session: EditorUnitLabTest", and the sim's own `__blueprints['uel0201']` had mass 81 and weapon 1 damage 72. First runs found three things: the play dropped mods missing from the list made at start, the map's remembered setup replaced the mods when the map was selected, and the test's later stages waited for the map view during the play.
- Derived units (the lab's Derive...: an id, a name, a description): a new unit id made from the selected game unit without copying a file. The project writes `hook/lua/system/Blueprints.lua`, which chains FAF's `ModBlueprints(all_bps)` (the way `lua/system/Blueprints.lua` tells mods to change blueprints in code), deep-copies the base unit's blueprint under the new id with `table.deepcopy`, merges the derived unit's changes with `table.merged` (weapons by their place, as merge blueprints) and sets `General.UnitName` and `Description`. Mesh, script, sounds and build menu entries stay the base unit's; the copy is taken after the base unit's own merge blueprint, so it carries those changes too. A derived unit has no merge blueprint of its own; the hook is removed when no derived unit is left. FAF Studio's hook called `BlueprintMerged` and `MergeWeaponByLabel`, which FAF's Lua doesn't have.
- The lab lists the project's derived units first; their fields are the base unit's with their own changes; Remove unit takes one out (an undo step, as Derive is).
- `/unitlabtest` also derives xel0201 "Lab Tank" from uel0201 with mass 156: the play logged "Hooked /lua/system/Blueprints.lua with /mods/editorunitlabtest/hook/lua/system/Blueprints.lua", 73 preset units instead of 72, and the sim's `__blueprints['xel0201']` had mass 156, name Lab Tank and weapon 1 damage 72 (uel0201's changed damage).
- Checks (in Mod project, live): the name and uid, a `mod_info.lua` on disk with another uid, units the game doesn't have (a merge blueprint would change nothing), derived units whose id the game has or whose base it lacks, derived units without a name or an icon (`/textures/ui/common/icons/units/<id>_icon.dds`; the build menu shows none), weapon changes whose label the unit lacks, keys that aren't blueprint paths, health 0 (error), build time or rate 0 or below, other values below 0, and changes not written yet. Errors red, warnings amber, notes grey.
- Zip for the vault: writes the project, refuses while a check is an error (it says which), and zips its files without the editor's own (`editor_project.json` and its `.bak`, half-written files) under one folder named for the project, as `<name>.v<version>.zip` in the vault's `editor_releases` folder (not in `mods`, so the game doesn't find it there). `/modtest`: with health 0 the release was refused with that check; then `EditorModTest.v1.zip` held `EditorModTest/mod_info.lua` and `EditorModTest/units/daa0206/daa0206_unit.bp` (read back with .NET's zip reader).
- **Unit viewer** (Units, right; `ui/EdUnitViewer.cpp`): the unit lab's unit (a derived unit's base) drawn by the game's model thumbnail renderer (REN_RequestThumbnail, as the prop pictures), turned by dragging or Heading / Pitch (Front resets), with its mesh, its levels of detail (cutoff, mesh file) and its scale. The renderer draws units unlit on an opaque black background, so the view is dark.
- Make icon: a render of the unit framed by its drawn part into a 64 x 64 DXT5 icon (`tools/EdUnitIcon.cpp`), written into the project as `icons/units/<id>_icon.dds`, where FAF's UI finds an active mod's unit icons (`UIUtil.UIFile` with checkMods); a derived unit then names it as its `Display.IconName` in the hook (a copy otherwise keeps its base unit's icon, a note in the checks). A render drawn edge to edge (no outline to frame) or too dark isn't written: with the thumbnail renderer that is every unit today, so Make icon says why and the base unit's icon stays. A lit render with a background that can be keyed out (FAF Studio renders on black and on white) is still to come.
- Binary files the project writes (icons) are listed in `editor_project.json`: the project writes over its own and refuses anyone else's (a DDS can't carry the generated mark).
- `/unitviewtest`: xel0301 derived from uel0201; the viewer lit 55,276 of 147,456 pixels; Make icon refused ("the render is opaque edge to edge"). Before the guard, a run wrote the icon (5,616 bytes, a 64 px DXT5 with mips), the flag and the hook's IconName, and decoding it showed it black (mean colour 0, 0, 8): hence the guard. A second run then found the first run's icon not the project's: hence the list of binary files.
- The Units list of the design is the Assets panel's Units tab (faction, tech, type, search, favourites, icons). Not here yet: a usable icon render, the new unit wizard (phase E8).

**Editor mods** (the Editor mods panel in Units; `doc/EdEditorMods.cpp`, `ui/EdModHost.cpp`; after FAF Studio's editor mod API, as commands since this editor's panels are native):
- A mod in the vault's `mods` folder whose `mod_info.lua` says `editor_mod = true` (and `editor_api = 1`, or none) adds commands from its `editor/commands.lua`. Editor mods are off until turned on in the panel; the turned-on ones are kept in the settings folder (`editor_mods.txt`; a test run only with `/editormods <file>`) and run when the editor starts.
- Each runs in a Lua state of its own: Lua's base library without `dofile`, `loadfile`, `require` and `loadlib`, no `io`, no engine functions, never the game's sim. The `Editor` table: `Command(id, title, fn [, keys])` adds `mod.<mod>.<id>` to the palette and the keys (Settings › Keys can rebind it); `Log(text)`; `Run(commandId)` runs one of the editor's commands (false when it can't run; a few deep at most); `Map()` is `{ path = ... }` of the open map, or nil; `ApiVersion`.
- A command that raises an error is logged with its mod's name, file and line, and turns that mod's commands off until the editor starts again; they say why in the palette and menus. A mod for a newer editor API isn't started (the panel says why).
- `/editormodtest` with the test vault's EditorModApiTest: turned on, 2 commands; the sandbox had no `dofile` and no `io`; hello logged the open map's path and ran `view.frame`; broken's `error()` was reported as `EditorModApiTest/editor/commands.lua(12): broken on purpose` and hello then refused with that reason. Seen on the way: indexing a nil value (`nothing.field`) didn't raise an error in this engine's Lua.
- **Effects into a mod project** (the particle editor's File > Save to mod project, while a project is open; `doc/EdEffectMerge.cpp`): each emitter of the open effect that came from a game file, or the open game beam or trail, becomes a merge blueprint naming that file (`Merge = true`, `Source = '/effects/emitters/x.bp'`; FAF's `EmitterBlueprint` / `BeamBlueprint` / `TrailEmitterBlueprint` take their id from Source and merge into the game's), at the same path under the project's `effects`. Entries are compared as the full writer writes them: a changed field is one line, a changed curve its whole block, an unchanged emitter is skipped. FAF merges table by table and can't take a key away, so a curve left with fewer keys than the game's, or a field taken out, writes the whole blueprint over the game's file instead (no Merge, the same Source; its first lines say why). An emitter of the effect's own is written whole at `effects/emitters/<name>.bp`. Save keeps writing the map's or the editor's folder as before.
- `/effectmodtest`: adisruptor_hit_01 with lifetime 1 to 8 and a changed curve (a merge of those two entries); aeon_light_displacement_missile_hit_02 with its EmitRateCurve cut from 3 keys to 1 and lifetime 1 to 4 (a replacement); in the play with the project on, the play's own rules had lifetime 8 and 4. The sim's Lua has no emitter blueprints, so the check reads the rules (RULE_FindEmitterBlueprintByName).

**Map info** (the Info panel's Edit map info; `doc/EdScenarioInfo.cpp`): the scenario's name, description, type (skirmish, campaign_coop, campaign), version (`map_version`) and no-rush radius. A field is set when it is left after typing (the type when picked); each change is one undo step ("map info") that puts back only that field, so other changes to the scenario (teams, water bodies) stay; a field the file didn't have goes away again. Save as new map folder is Ctrl+Shift+S.

## Play

**Play of unsaved edits** (`EdDocument::WritePlayCopy`, the app's DrivePlayCopy): Play on the open map while it has unsaved edits starts a copy of it with the edits: `<vault>/maps/<map>_editor_playtest`, its files and names as Save as new folder writes them (one copy routine for both), mounted at `/maps/<folder>` as the game's init mounts the vault's (a folder made while the editor runs isn't mounted otherwise: the first try gave "Unable to load map"). The document's own files, save target and saved state stay as they were. The copy is removed when the play ends, and before the next one is written; only a folder ending in `_editor_playtest` is ever removed. A map without unsaved edits plays as saved. A test vault map with a start moved 8 units (`/playcopytest`): the copy of 11 files loaded and played; Stop removed it; the map stayed modified.

The toolbar over the panels (flat buttons in groups with thin rules between them, as the mockup's; a pressed toggle in the accent's soft fill) starts with **Play** (F5, green, its setup in the arrow beside it), then New, Open and Save (Save as is in the File menu), Undo (naming its step) and Redo, the **symmetry** tiles (None, Left-right, Half turn, Both axes, Quarter turns; all ten are in the Terrain tool), Grid, Snap and the grid's step (Grid draws the cell edges on the ground around the cursor; Snap puts markers and props placed or dragged in a cell's middle, while mass and hydrocarbon points always sit on half units as the game's saves place them; `/grid`, `/snap`, `/gridstep <n>` for test runs), then On ground and the map border (Grid and Slope are the view's, below), and at its right **Check** (runs the map check and shows the Check panel) and **Release** (the vault package), then the **UI scale**: one joined group, - / the scale in percent / +, stepping 75 to 200% (the middle resets to 100%). The panels' sizes are scaled from the style made for the screen's DPI (`ImGuiStyle::ScaleAllSizes`) and the text by `style.FontScaleMain`; sizes the panels lay out by hand go through `Em()` (`ui/EdUiScale.h`, pixels at the 16 px base font). The scale is kept in `layout.ini` as `[FafEditor][Ui] Scale=<x>`, the same for every map; `/uiscale <x>` sets it for a test run. The panels' tab titles get 9 x 5 px of padding (ImGui's default is 4 x 3). Pick a map in the Map panel (each map by its title, then its folder name; type to filter; double-click opens it for editing) or in Play > Map, and press **Play** or F5. The map loads and plays inside the editor's view, between the panels, with the game's own interface. **Stop** or F5 returns to the editor. So does the game's own way out of a session: its menu's exit, quitting from the score screen, and "Exit to Windows", which stops the play instead of closing the editor. View > Panels while playing (on by default) hides the panels during play when turned off, so the game takes the whole window. The window's title says what plays. **Editor view / Game view** (F6, or the switch beside Stop, while a play runs): the editor's view of its map comes in front of the play, with its camera, tools and overlays, while the game runs on behind it; F6 again gives the game's view back as it was. The renderer draws one map at a time (`sWldMap`): the editor's while its view is in front, the session's again after; an engine addition, `moho::gViewportOnlyView`, has the viewport draw only the editor's world view while the session's stay registered, `ren_Ui` leaves the game's interface undrawn, and mouse and keys the editor's view doesn't take are kept from the game (a click must not order its units). The session keeps its own map for everything it does (`CWldSession::mWldMap`), so nothing of the play changes. The game's own units show in the editor's view, and so do the map's props and placed units (WPE.51): between plays the view draws them with the rules the editor keeps (`RULE_PeekKept`), and in front of a play with the same rules lent to it (`RULE_PeekLent`, an engine addition), which become the kept ones again when it ends, so what the view drew stays good past the play's end; before the next play takes the rules the view lets go of them, as between plays. The map's placed units are the map's (what its `_save.lua` places): the play's copies of them are game units, shown as well, at the same places until they move. On SCMP_009 two plays in a row, each ended behind the editor's view (`/playseconds 12 /playcycles 2 /playeditorview 4,0`), drew 5182 props and 43 units in front of each, with nothing missing and no error. A play that ends behind the editor's view leaves the editor on its map. Each view keeps its camera across the switch: the game's is untouched, and the editor's comes back where it was left for the same map (a newly opened map starts framed whole). `/playeditorview <on>,<off>[,<on again>]` (seconds into a `/play`) for test runs; each switch logs both cameras. On SCMP_009 the game's camera was at 672.5,346.5 zoom 40 before and after, and the editor's, zoomed and dragged to 159.0,331.9 at 561.3 before the switch, came back there. **The game's units in the editor's view** (`view/EdLiveUnits.cpp`, `ui/EdLiveUnitPanel.cpp`): with the Select tool a click picks the play's own unit nearest it (Ctrl adds or takes out), a red ring marks each, and a drag warps them by as much (the sim's `Warp`, on the ground there). The Properties panel then shows the game unit: its icon, name, blueprint, army and entity id; its health (a slider, Full) and veterancy (FAF's `SetVeterancy`); its blueprint's toggles as the order panel has them (shield, intel, jamming, production, stealth and cloak "on" while their script bit is clear); its enhancements by slot (ticked to add, `CreateEnhancement`, at once; unticked through the `<name>Remove` enhancement where the blueprint has one); Kill and Remove. The state is read through the game's UI Lua (`GetUnitById`, its blueprint, `GetScriptBit`, `EnhancementCommon.GetEnhancements`); each change is the game's own call in its sim (`SimLua`; the editor's plays have cheats on), and none touches the map's files. "Game units" beside the switch hides them in the editor's view (not drawn, not picked). `/playlivetest` (with `/playeditorview`) for test runs: SCMP_009's Cybran commander, 10000/10000 at 672.5,346.5 with none of its 10 enhancements, became 5023/10000 at 692.5,346.5 with Teleporter. **Editing while it plays** (investigated for WPE.39; the editor's own solo playback, never multiplayer): a play is the game's own session, loaded from the map's files into a world map of its own (`EdPlay::StartSession`, `EditorStartPlay`), and its sim holds a copy of the heights (`STIMap::STIMap(STIMap*)`, 0x00577890, copies the samples). The sim is the heights' source: each beat hands its height field to the user side (`SSyncData::mTerrainUpdate`), and `CWldTerrainRes::SyncTerrain` copies the changed rectangles into the rendered terrain, but only those the camera sees, zoomed in past `ren_SyncTerrainLOD`, and visible to the focus army. `/playterrainpoke x,z,size,height` (with `/play`) proves the sim half: on Seton's Clutch `SimLua FlattenMapRect(502, 502, 20, 20, 120)` left the sim's height at the centre 120 (its own log) while the rendered height stayed 18.48 (the centre was out of the camera). So live edits can go in: heights through the sim, between beats (as `FlattenMapRect`: the samples, the changed rectangles, units on the area re-seated), with the rendered terrain synced for the edited rectangles whatever the camera; texture layers, masks, decals, water and lighting straight into the session's world map (they are only the renderer's); the session's units shown or hidden by culling their meshes. The path data isn't rebuilt by a height change (`FlattenMapRect` doesn't either). **Heights made in the editor's view reach the play** (WPE.40, `view/EdLiveTerrain.cpp`): each rectangle a height tool, undo or redo changes is copied into the session's rendered terrain at once (`SetElevationRectRaw`, then `NotifyMapChanges` one sample wider for the normals), whatever its camera sees, and queued for the sim, which takes it at the start of its next beat on its own thread through an engine addition, `moho::gSimBeforeBeat` (`moho/sim/SimEditorHook.h`, called first in `Sim::AdvanceBeat` and empty in every exe but the editor's; a `std::atomic` read once per beat, since the editor sets and clears it from its own thread, and the two switches it reads, no reseat and no path redo, are atomics too). The queue and the hook go when the play stops. A play of another size than the map's is left alone. `/playheighttest` (with `/playeditorview`) for test runs: a raise 25 units beside SCMP_009's first commander took the editor's height at 698,346 from 18.82 to 48.82, the play's drawn terrain read 48.82 there at once, its sim 18.82 -> 48.82 at the next beat (its own log), and the sim's Lua `GetTerrainHeight` 48.82 (that run's version of the test). After the heights, the sim's path clusters over the changed area (4 cells wider) are marked dirty (`PathTables::DirtyClusters`, so they are worked out again from the new slopes), and the land and seabed units standing on it are put back on the ground as `Sim::FlattenMapRect` (0x0074B120) does: a moving unit through its motion's next surface pass, a structure by a warp in place (WPE.47). The test now raises under SCMP_009's first commander: it stood at 48.68 on ground raised from 18.68 to 48.68; with `/playnoreseat` (the re-seat off) it stayed at 18.68, under the ground. `/playridgetest` (with `/playeditorview`) raises a steep ridge 35 units east of the first commander, 64 units long, orders the commander 70 units east and logs where it is every 2 s: on SCMP_009 it went round the ridge's south end (40 units off the line at 30 s) where with `/playridgeoff` (no ridge) it walked straight east (1 unit off the line, 48 units on); with `/playnopathdirty` (the clusters not marked) it took the same way round, step for step, so the sim's path search sees the new ground by itself and the marking is a harmless extra. **Lighting, water, masks and layers reach the play too** (WPE.41): while the editor's view is in front of a play, the document holds the play's map (`EdDocument::SetLiveMap`), and each lighting and water edit (and its undo) is written into it as into the editor's (sun, ambience, shadow fill, specular, bloom, fog; the water's levels, shader numbers and textures, and its water map). The water's levels also go into the sim at its next beat through the same hook as the heights, so what floats and what is under water follows them. Mask strokes send the same rows to the play's terrain (`UpdateStratumMask`) when its masks are the map's size, and a layer's texture change goes into the play's strata. Decal edits go in too (WPE.49): each placement, path, deletion and move, and their undo, is the change between two snapshots of the decals, and `MirrorDecals` (`tools/EdDecals.cpp`) makes that change in the play's decal manager, matching decals by their saved fields rather than by index (`DecalKey`), so a decal the play loaded from the map's file is found by what it is. `/playdecaltest` (with `/playeditorview`) for test runs: on SCMP_009 (2236 decals in both) a decal added beside the commander was in the play at once (2237); the map's own boulder decal moved 40 units was gone from its old place in the play and there at the new one; putting the map's decals back as undo does left the play at 2236 with neither. `/playlooktest` (with `/playeditorview`) for test runs: on SCMP_009 the play's sun colour went 1.38,1.29,1.14 -> 2.00,0.40,0.30, its drawn water 17.50 -> 23.50, its sim's water 17.50 -> 23.50 (the sim's `GetSurfaceHeight` 23.5 over ground at 6.09 at 150,150), and its stratum 4 mask at the painted texel 140 -> 255.

The Map panel sets the play up, the way FAF's `/map` quick start does (`SinglePlayerLaunch.lua`) but with these choices:

- **Solo** (default) or **Against AI** with one of the game's AI types for every other army. Solo is the faster start: with no AI there is no AI map analysis (SCMP_009, second play: 2.3 s to the game solo, 4.5 s against "rush").
- **Faction**: random or one of the game's factions.
- **Fog**: fog of war ("explored") or none. The sim fixes fog when the game starts, so it applies from the next Play.
- **Keep this setup for this map**: on, the map keeps its own setup, saved at each Play; off, it plays with the setup of the last Play on any map. Picking a map takes its own setup or the last one. Kept in `%LOCALAPPDATA%\FAForever\Editor\play_setups.ini` by map folder name without its `.vNNNN` version, AI and faction by their keys. Test runs from the command line read it but don't write it. **Quick start** (on by default, kept with the setup): the commanders are there and take orders at once instead of FAF's warp-in, which hides each one for 3 s (`ScenarioUtilities.CommanderWarpDelay`) and then plays 2.1 s of effect (`CommandUnit.PlayCommanderWarpInEffect`), and the camera starts over yours instead of FAF's zoom to it a second in. As the play starts the editor sends the sim three short `SimLua` lines (its plays have cheats on): each commander shown as the effect's end leaves it (its blueprint's `WarpInEffect.HideBones` hidden again), its order queue opened, and a `PlayCommanderWarpInEffect` of its own that does nothing, since FAF looks that call up on the unit when the 3 s are over. The camera is framed on your commander in C++ as `UIZoomTo` (0x00867240) frames it; the game's `GetArmyAvatars` called from the editor's Lua fails LuaPlus's same-state check when it fills its table. With Prebuilt units on FAF has no warp-in, and only the camera is moved. On SCMP_009 the commander was shown at tick 7 and the camera was over it at the first playing frame; `/playnoquickstart` gives FAF's own start for comparison.
- **Slots** (the Play button's arrow, or the Map panel): each army slot as You, an AI (any AI type, AI mods' included: FAF's `lua/AI/CustomAIs_v2`) or empty, with its team (armies of one team start allied, as the lobby's teams) and an AI's faction; no You row watches the AIs as an observer. Victory, unit cap and the AI cheat multiplier as the lobby sets them, and sim mods to play with. **Profiles** keep a setup by name; the built-in ones are Solo sandbox, You vs 1 AI, 2 v 2 with AI, Free for all with AI and Watch 4 AI. SCMP_009 with M28AI plays without errors; 2 v 2 starts armies 1 and 3, and 2 and 4, allied. `/playprofile <n>`, `/playlogarmies` for test runs.
- **Hide the fog** and **Observer view**, during play: the first leaves out the fog's shading while you keep your army (a render-only switch, `ren_FogOfWarHidden`, as `ren_FogOfWar` is set by the sim every beat); the second switches to an observer's view (every army, no fog) and back. Editor plays have cheats on for this, without changing the `debug.enable_debug_facilities` preference the game reads. `/playnofog` for test runs.

Campaign maps go through FAF's own campaign setup. No replay is written.

How fast a play starts:

- The game's rules (every unit, projectile and effect blueprint, about 1.5 s to build for FAF) are built on a thread of their own when the editor starts, for the mods a skirmish uses (`RULE_PrepareKept`), and each play's rules are kept for the next one (`RULE_SetKeepBetweenSessions`). A Play pressed before they are ready waits for them. The game builds them for every session.
- Loading shows one line of text in the view ("Loading Seton's Clutch ...") instead of the game's faction movie, "IN TRANSIT" screen and loading tips, and the game's panels come in as soon as the map is ready instead of after the "IN TRANSIT" picture fades (`InstallLoadingView`, through `moho::gUIBeforeStartGameUI`).
- Solo, a Play 5 s after the editor starts reaches the game in about 2.3 s on SCMP_009 and 2.7 s on Alpha 7 Quarantine (SCMP_021, 40 km); later plays in 1.0-1.3 s and 1.6-2.0 s (Direct3D 12, Vulkan). On SCMP_021 two engine changes do it: the 3584 building skirts its start flattens update the terrain normal map one tile at a time for all of them (`IWldTerrainRes::NotifyMapChanges`, 30 ms where one update per skirt took 1.6 to 3.3 s), and a whole-map normal-map rebuild after the map changed is encoded on 4 threads as the loader's (0.4 s, from 1.6 s).

`/play` takes several maps separated by commas; the runs take them in turn.

The window is always one maximized, movable, resizable window, whatever the game's display options say; the game's own display option doesn't change it either. The panel layout is kept in `%LOCALAPPDATA%\FAForever\Editor\layout.ini`; View > Reset layout restores the default.

**The title row** (`ui/EdTitleBar.cpp`, `ui/EdWindowChrome.cpp`; as Discord and VS Code): the editor draws its own title row and Windows draws no caption. The row holds the app's mark, the open map's title with an orange dot while it has unsaved changes (and what a play is doing), the menus (File, Edit, View, Play), a search box that opens the command palette, and Windows 11's minimise, maximise and close at the right end. Its empty parts drag the window, double-click maximises or restores, and a right click is the window menu; hovering maximise shows Windows 11's snap layouts. Alt or F10 opens File, Alt and a menu's underlined letter that menu (not during a play: the game has Alt then). How: the frame's handler (`EditorFrameProc`) makes the whole window client area (`WM_NCCALCSIZE`; a maximised window keeps its hidden border off-screen) and answers `WM_NCHITTEST` from the row's layout: `HTCAPTION` over its empty parts, `HTMINBUTTON`/`HTMAXBUTTON`/`HTCLOSE` over the buttons (it presses them itself on `WM_NCLBUTTONUP`, so Windows draws no classic buttons over them), `HTTOP` along the top edge; the panels' window, which covers the client area, answers `HTTRANSPARENT` there so the frame decides. The window keeps `WS_OVERLAPPEDWINDOW`, so Aero Snap, Win+arrows, the shadow and Windows 11's rounded corners stay; its border is dark (`DWMWA_USE_IMMERSIVE_DARK_MODE`). `/nativecaption` keeps Windows' caption (the row then only carries the menus). The row logs its layout when it changes (`title row <h> px high ... buttons at x ...`); test runs read it and ask the window `WM_NCHITTEST` at each part.

**Commands** (`ui/EdCommands.cpp`): every menu entry is a command of one registry, with an id (`file.save`), title, category, keys (one or more chords, written one way: `Ctrl+Shift+Z`), and, when it can't run now, the reason, which the menu shows greyed with the reason on hover. The old menu ids still run their commands (`WM_COMMAND`, as test runs post them). **Command palette** (`ui/EdPalette.cpp`; Ctrl+K or Ctrl+Shift+P, also over the view, or the title row's search box): every command found by typing a few of its letters (in order, case aside; word starts and runs count more), the ones run last first when nothing is typed; Up/Down pick, Enter runs, Esc closes; a command that can't run says why in its row and stays unrun. The log says what the palette ran. `/command <id>[,<id>...]` runs commands by id and `/palette <text>` opens the palette with the text typed, both at frame 300, for test runs.

**Keys** (`ui/EdKeymap.cpp`, `ui/EdKeysPage.cpp`; File > Settings, View > Keyboard shortcuts): every key is a command's, so each one can be changed. One dispatcher runs them from the panels and from the view (EdApp.cpp: the first command bound to the key that can run now; a command that can't says why in the log). While a play has the view, only the keys of Play/Stop (F5) and the editor's view (F6) are the editor's; the game keeps every other key. In the panels a text field keeps its own keys (letters, digits, Delete, Ctrl+A/C/V/X/Z/Y, Ctrl with the arrows) and ImGui's keyboard navigation keeps the arrows, Space, Enter, Tab and Escape; F-keys and Ctrl+S still work while typing. The defaults: Ctrl+N/O/S, Ctrl+Z and Ctrl+Y or Ctrl+Shift+Z, Delete, Ctrl+C/V/D (copy, paste at the cursor, a copy 8 units beside), 1 to 8 the tools (the strip shows each tool's key), Home frames the map, Ctrl+= / Ctrl+- / Ctrl+0 the panels' scale, Ctrl+K or Ctrl+Shift+P the palette, F5 Play/Stop, F6 the editor's view during a play. The view's own keys (W/A/S/D and the arrows move the camera, Shift faster, Q/E turn the selected props, Enter/Backspace/Escape for decal paths and water outlines) aren't commands yet. **Settings > Keys** lists every command by category with two keys: a click on one waits for the next key (Escape keeps the key, Backspace takes it away); a key another command has turns amber on both rows, each saying which other command it runs, with "Take it from there"; Reset puts a row back, Reset all every row. The keys you changed are kept in `%LOCALAPPDATA%\FAForever\Editor\keys.ini`, one `<command>=<keys>` line per changed command (an empty value for none), written at each change; a line it can't use (no such command, a key it can't read) is a warning in the log and the rest applies. `/keysfile <path>` reads and writes another file, so a test run leaves yours alone.

**Workspaces** (`ui/EdWorkspaces.cpp`; the title row's tabs, Alt+1 to Alt+0, View > Workspace, or the palette): ten sets of panels, each in a dock layout of its own, for one kind of work: Terrain, Objects, Environment, Layout, Generate, Mission, Effects, Units, Materials and Review. Each keeps its own layout (moved and resized panels stay where they were put when you come back) and which panels it shows: a panel closed in one stays open in the others. Each panel is a window of its own per workspace (`Tools###Tools@objects`), so ImGui keeps every layout in `layout.ini` by itself; Terrain keeps the window names from before workspaces, so a layout saved then carries over. The workspace shown last and each one's panels are kept in `layout.ini` (`[FafEditor][Ui] Workspace=<key>`, `Panels.<key>=<ids>`); a test run (any of the editor's test options: `/command`, `/play`, `/check`, `/tool`, `/uiscale`, ...; the list is `IsTestRunCommandLine` in EdApp.cpp) writes back the ones it read. View > Reset this workspace's layout lays the workspace shown out as it started, with its first panels. Review only looks: the tools other than Select, undo, redo, delete, paste and duplicate say "the Review workspace only looks" and don't run. Each workspace starts with the panels there are now (Terrain as the editor was before workspaces; Effects with the particle browser and editor; Materials with the material editor; Mission with the script editor and the adaptive map window); the design's other panels (Layers, Outliner, Problems, History, the node editors) join theirs as they are made.

**Status bar** (the window's bottom row; `ui/EdStatus.cpp`): the renderer with a green dot and the GPU, the mode (Editing, what a play is doing, or "Review (read-only)" in the accent colour), the problems ("2 warnings" with a warning sign, or "no warnings"; a click opens the Problems panel), the cursor's place and height, the ruler, the selection as a count ("3 markers selected", "nothing selected"), the step Undo would take back ("undo: height stroke"), then at the right end the last message with how long ago ("Saved scmp_009 (2 min ago)"; saving, keys written and workspace switches post one; "Unsaved changes" when there is none) and the frame rate. **Settings** (File > Settings, View > Keyboard shortcuts, or "Settings: ..." in the palette; `ui/EdSettings.cpp`): pages on the left, the picked one on the right. **General**: full help text, the panels while playing (both also in View), and the settings folder with Open. **Appearance**: the theme (with Reload and the themes folder), the panels' scale (75 to 200 %), and the title row: the editor's own or Windows' caption (for remote desktop and screen readers), from the next start. **Keys**: as above. **Viewport**: the renderer (Automatic tries Direct3D 12, then Vulkan; or Direct3D 12 or Vulkan first), from the next start, with the one in use; and the frame rate behind other windows (10, 30 or 60 fps, or no limit; 30 at first): while another window is in front and no play runs, the editor waits between frames so the GPU rests. **Performance**: the renderer, GPU, frame time and CPU threads in use; GPU compute and thread counts are set there once the tools that use them have them. **Autosave, recovery and backups** (`doc/EdAutosave.cpp`; Settings > General): while a map with files of its own on disk has unsaved changes, the editor writes all of its files (the `.scmap` and its Lua files, as Save would) into `%LOCALAPPDATA%\FAForever\Editor\autosave\<map folder>\` with an `autosave.txt` naming the map, once the interval (every minute at first; 2, 5 or 10 in Settings) has passed since the changes began or the last autosave and nothing was pressed for 3 s, never during a play; the status bar says "Autosaved HH:MM" and the log how long it took. The map stays unsaved: an autosave moves nothing Save compares against. Saving the map, or "Don't save", removes its autosave, so one left at the next start was left by a crash or a close without saving: the start offers it ("Recover unsaved work": Recover, Discard, or Later), as does File > Recover an autosaved map and the start screen's Recover. **Terrain brush:** with the Terrain tool, the left mouse button held over the opened map paints heights with the panel's mode (Raise, Lower, Smooth, Flatten to the height under the stroke's first point, Set height to the panel's height, Noise, Terrace to the nearest step, Plane through three points Ctrl+clicked on the terrain, Stamp: a height image added over the brush's square once per click, white adding the stamp height times strength, Erode: thermal erosion, where the ground between two neighbours is steeper than the panel's talus slope height moves from the higher to the lower until it isn't, each pair's exchange equal and opposite so ground is moved downhill and none is made, at up to 60 full steps a second times strength, at most one a frame, since a change scaled like the other brushes' would round to nothing on gentle ground at 60 fps, Water erode: hydraulic erosion, droplets dropped at random in the brush (600 a second times strength) run downhill with a little inertia, take ground where they speed up and leave it where they slow or climb, and leave what they still carry where they stop, so channels and fans form and no ground is made; it runs around the cursor's copy of the brush and writes each changed sample to its whole symmetry group, rounding at random but evenly from a seed the stroke advances every step, Rain and Deposit: FAF Studio's erosion brushes on the terrain library's erosion session (`terrain/EdErosion.cpp`, `ErodeSession`), which keeps the map as floats for the whole stroke; Rain's droplets run on past the brush and keep digging downhill up to 0.8 of the radius beyond it, and part of what leaves the brush is carried away (70% is put back low inside it); Deposit lays an even heap of sediment under the brush (0.5 units at the centre per 15th of a second at full strength) that the water carries a little downhill, so ground is made; right-dragging Water erode deposits; the session simulates the cursor's copy, every changed sample is written to its symmetry group and stored back into the session, so a dab across a mirror line reads what the last step wrote; undo saves the whole window, Rain's reach included; `/brushtest <mode>,<x>,<z>[,<seconds>]` runs a scripted stroke for test runs and logs the samples changed, the ground added or taken and the farthest change; on SCMP_009 (half-turn symmetry, two copies, radius 14, 2 s) Water erode changed 1,253 samples with -1.8 units, Rain 1,996 samples reaching 25.0 from a centre with -18.0 units, Deposit 1,200 samples with +8,605.5 units), radius, strength, falloff and symmetry (`tools/EdHeightBrush.cpp`). From FAF Studio's brushes: Plateau brings the ground to the stroke's level in one step where the brush is full (strength 0.5 and more), the falloff shaping the shoulder; Sharpen pushes the ground away from its blurred self (right-dragging Smooth does it) at 1.5 a second times strength, since it feeds on its own result and Smooth's rate would multiply the relief some fifty times a second; Smooth and Sharpen blur the ground twice with a box that widens with strength, 3 x 3 when weak up to a quarter of the radius (at most 6 samples each way); Noise is smooth value noise (bump size, 1 to 4 detail layers, roughness), a new pattern each stroke. Every mode that paints sample by sample takes a shape (Round follows the falloff; Square, Diamond, Cone, Plateau, Ring, Ridge, Mountain, Rocks, Bump are masks over the brush's square, turned by an angle). Shapes and stamps are read in the cursor copy's frame: a group's weight is the strongest the cursor's dab gives any of its members (for N-way turns, each copy's offset turned back), so every symmetric copy is the mirror or turned image of the cursor's dab; read at the nearest copy instead, a group whose first member lies by another copy came out unmirrored there (`ShapedDabUnderSymmetryIsTheCursorsDabAtEveryCopy`, `ShapedDabUnderFourTurnsIsTheCursorsDab` fail that way). Brush library (`tools/EdBrushLibrary.cpp`): greyscale images (PNG, TIFF, BMP, R16, RAW) in `%LOCALAPPDATA%\FAForever\Editor\brushes` are listed in the shape picker after the procedural shapes and read at 129 x 129; Import to library copies a picked image there. Stamp (FAF Studio's stamp.lua): its source is a picture file, a procedural shape or a library image; Add and Subtract press it into the ground, Max raises the ground to it, Min lowers it to it turned upside down, Replace sets the ground inside its circle to it, the last three measured from the ground under each dab or under the stroke's first; each dab can turn (a set angle plus a random turn), vary in size and move by up to a share of the radius; with a spacing (a share of the stamp's width) a drag stamps along its path (`StampDabsAlong`), without one it stamps once per click. `/stampsource <n>` (1 to 9 the shapes, from 10 the library's images) and `/stampstroke <spacing>,<random turn>,<size>,<place>,<mode>` set a stamp for test runs, and `/brushtest 8,<x>,<z>,<seconds>` drags it 40 samples; on SCMP_009 a Mountain stamp in Max mode at spacing 0.5 (14 samples) put 3 dabs down along the drag (6 rectangles over the two half-turn copies) and one per click put down 1. `/brushshape <shape>,<degrees>` sets the shape for test runs; on SCMP_009 (radius 14) Plateau for 0.5 s changed 1,169 samples, Sharpen for 1 s 392 samples with +5.6 units, Smooth for 1 s 881 samples with -0.1 units, and a Raise with the Ridge turned 30 degrees 513 samples, all within 13.9 of a centre. Limits leave alone the vertices outside a height range or steeper than a slope (judged at each symmetry group's first vertex, so copies stay identical). `/brush <mode>` (9 is Erode, 10 Water erode), `/erodetalus <slope>` and `/stamp <file>` set the mode, the talus and the stamp image for test runs; each stroke logs how many samples it changed. On SCMP_009 a three-second Erode stroke on the rocky ground at the view's lower left changed 442 samples at the default talus 0.6 and 824 at 0.2, the hollow under the cursor filling from 26.05 to 27.09. A four-second Water erode stroke there changed 1326 samples. Symmetry is exact: each group of mirrored samples gets one new height, computed from its first member, written to all of them, so mirrored halves stay identical and a stroke on a mirror line applies once (GoogleTest `faf_editor_brush_tests`). N-way turns (2 to 16 copies, the panel offers 3 to 8) can't be exact, as their copies fall between vertices: the first sector (from the map's centre towards +x, turning towards +z) is painted, and every other vertex the brush covers, plus 2 vertices past its edge, takes the height at its point turned back into the first sector, read between vertices; 4 turns are exact. The diagonal and turn modes paint without symmetry on a map that isn't square. The symmetry's mirror lines are drawn along the ground with a translucent wall standing on each (the turn centre as a vertical axis, the sectors' edges for N-way turns), and the brush shows as rings on the terrain at every copy (white at the cursor, orange at the mirrored ones; the inner ring is where the falloff starts), drawn through the renderer's editor hook (`ED_SetHook`). Edit > Undo and Redo, Ctrl+Z and Ctrl+Y (or Ctrl+Shift+Z) in the view or the panels, take back whole strokes, byte for byte (`undo/EdHeightHistory.cpp`: the 32 x 32 tiles a stroke touched, before and after; 256 MB at most, the oldest strokes go first).

**Texture painting** (Tools panel, Texture; `tools/EdMaskBrush.cpp`): the paint list shows the map's strata 1 to 8 by texture name (the lower layer lies under all; the upper one is blended by its own alpha). Paint raises the chosen stratum's weight, Erase lowers it, Smooth evens it out; "Lower the layers above" makes Paint lower the strata blended over the chosen one by as much, so it shows. The brush's radius, strength, falloff, symmetry and limits are the terrain brush's; symmetry is exact on the masks' texels as on heights (N-way turns paint the first sector and copy the nearest turned-back texel). Weights move by whole steps with a per-step dither, so weak strokes still reach full. Rules set a stratum to full where the ground lies in a height range and/or slope range, over the whole map, in order (Apply rules to whole map, one undo step). **Mask generator** (the Texture tool's Mask generator section; `tools/EdMaskGen.cpp`, FAF Studio's maskgen.lua): a list of rules that makes a 0..1 mask over the whole map from the ground, on the field library. Source rules (slope with an optional fractal wobble of its limits; unit class slope, the engine's footprint rating for land units of 1, 2, 3 and 5 squares or the structures' ground variation, passable or blocked; height band, with a wobble and a sun side that starts higher; curvature; relief above the blurred surroundings; aspect; water above, under or a shore band; shore width along the ground; noise of five kinds; flow (drainage); position, linear or from the middle; a texture layer, all of it or where it shows; free of the layers above; near a layer; constant) combine with what the rules above made by AND (the smaller), OR (the larger), multiply, minus or add, and may be inverted; modifier rules change the result so far (not, blur, grow, shrink, remove specks, fill holes, threshold, smooth step, amount, ragged edge, fine grain). FAF Studio's twelve starting points fill the list (cliffs, ground land units cannot cross, buildable flat ground, beach, snow caps from the map's own height range, ridge tops, gullies, sun-facing slopes, dirt patches, shore foam, deep water, map edge band); each rule opens to its values, can be switched off, moved up or removed, and "Add a rule..." lists every type. The preview (red on dark, 160 px) and the share of the map it covers are made again a moment after the last change while the section is open. Write into layer N puts the mask into a layer by Replace, Add to (the larger) or Subtract from, at a strength, optionally only where the layers above leave the ground free, in the shader's mask range, as one undo step; the brush's symmetry then copies that layer's texels from the source part to every copy. The imported-mask source of FAF Studio is left out (no import slots here). `/maskgen <preset>,<layer>[,add|,sub][,free]` writes a starting point into a layer for test runs. On SCMP_009 the cliffs starting point written into layer 3 (evrock008) changed 36,295 texels in 0.03-0.05 s and left the rock on the steep bay walls only (layer 3: 8.2 % of the map before, 3.3 % after), one undo step, with the map's half-turn symmetry.

**Mask brush options** (FAF Studio's strata brush on the editor's exact mask brush, `tools/EdMaskBrush.cpp`): Paint stops at its Up to share of full weight (ground already above it stays). Without Build up (the panel's default) a stroke keeps the texels as they were when it began and each texel's coverage, the strongest weight times strength any of its steps gave it; the texel is its start value blended towards the target (Paint) or nothing (Erase) by that coverage, so going over a spot again adds nothing and the edge keeps the brush's profile (`MaskStroke`). Build up adds every step, as before. Scatter takes up to its share of a texel's weight by a hash of the group's first texel and the stroke, so every copy speckles alike; Steeper than leaves gentler ground alone. The brush takes the height brush's shapes and library images, read in the cursor copy's frame. `/maskoptions <up to>,<scatter>,<min slope degrees>,<build up>` and `/masktest <layer>,<x>,<z>[,<seconds>]` drive it for test runs: on SCMP_009 layer 3, a second at strength 0.5, Up to 50% and scatter 60% left 294 texels changed with at most 63 of 255 (half the target: the coverage is weight times strength); Build up at 100% reached 255.

**Mask encoding** (`RemappedStrata`, `MaskWeight`, `MaskStoredFor` in `tools/EdMaskBrush.h`): the bytes in a map's stratum masks show differently under different terrain shaders. FAF's `effects/terrain.fx` reads a mask byte m either as `saturate(2m - 1)` (the half range: bytes up to 127 show nothing, 255 shows all) or as it is (the full range). TTerrain, TTerrainXP, TTerrainGlow, TTerrainXPExt and Terrain301 read the half range; the numbered shaders pass a `halfRange` flag to their pixel shader, set exactly when the name's middle digit is 5 (Terrain050, Terrain151, Terrain252B ...), and the 1xx / 2xx ones leave stratum 8, their roughness multiplier, in the full range; the others (Terrain000, Terrain101B, Terrain200 ...) and TerrainPBR read the full range. The table was first derived from the `2m - 1` lines alone, which sit inside `if (halfRange)` in the numbered shaders, and so treated the full-range ones as half range (every composite technique's albedo call is now checked in `MaskEncodingTests`). The brush, Smooth, the weight overlay, the coverage figures, mask import and export and the material editor's mask output (applied with a graph to strata 1 to 8) work in the weight the map's current shader shows and store the byte for it (a remapped zero is stored as 127; a texel a stroke leaves at the same weight keeps its byte). Texture rules write full weight, which reads the same either way. When the masks are read, a stratum the shader remaps that has paint but none of it showing (every painted byte 1 to 127: painted for a shader that reads masks as they are) is reported in the log and the Problems panel; soft edges next to paint that shows are not (GPG's own maps fade through them: 152,660 such texels on scmp_009). Changing the shader keeps the masks as they are; when the new shader reads them differently the log says the paint so far will show differently, and the brushes encode for the new one from then on. The masks-read log line names the shader and the strata it remaps.

**Shader browser** (Texture tool, Browse beside the shader picker; `tools/EdShaderProfiles.cpp`, FAF Studio's shaders.lua): the game data's terrain shaders by family (Original, Extended 0xx, PBR 1xx, PBR with height splatting 2xx, older or unknown), the map's marked. For the chosen one: what it does, how its masks are read (the same table the brushes use), how many layers it paints, how to make its textures, a table of what each layer's albedo and normal map hold (Base, layers 1 to 8, Upper; the B shaders' layers 3 and 4 are mapped only from the side), its notes, and a warning when it reads the masks differently from the map's shader. Use this shader switches like the picker, as one undo step; the paint keeps its bytes. The Terrain1xx and 2xx profiles are made from the name (lighting digit, range digit, macrotexture digit, B); a shader the table doesn't know gets a plain entry. `/shaderbrowser <name>` opens it for test runs.

**Convert layers** (the shader browser's Convert section; `tools/EdLayerConvert.cpp`, the masks part of FAF Studio's stratumconv.lua): converts the map's paint to the chosen shader and switches to it, as one undo step (a `LayerConversion` edit: the masks before and after, the layer slot moves and the shader). The paint is re-encoded when the two read the masks in different ranges, so it looks as it did (bytes are kept exactly where the range stays); painted layers the target doesn't draw (TTerrain draws 1-4, the numbered shaders 1-7) move with their texture to a layer that holds no paint (untextured first), or merge into a chosen layer, or are dropped; for the 1xx and 2xx shaders layer 8 becomes the neutral roughness multiplier (128); for the biplanar shaders the two layers painted on the steepest ground (at least 20 degrees on average) move to layers 3 and 4. The plan, its warnings (what the textures still need: the roughness atlas, the splat settings, layer 8's map-wide data, an inverted albedo alpha) and the report show in the browser. Terrain301 and shaders the editor has no layout for are refused. `/convertlayers <shader>[,move|merge|drop][,undo]` runs one for test runs and with undo checks Undo and Redo against a hash of the masks and the shader: SCMP_009 (TTerrain) to Terrain151 changed only layer 8 (both read layers 1-7 in the half range), X1CA_001 (TTerrainXP) to Terrain101B re-encoded to the full range, moved layers 4 (31 degrees) and 2 (30 degrees) to 3 and 4 and merged layer 8 into 7; both came back exactly on Undo and Redo.

**Symmetry on open** (`DetectSymmetry`, `tools/EdSymmetryCheck.cpp`): maps don't store the symmetry they were made with, so while a map loads its heights, start positions and resource markers are compared with their copies under each mode (FAF Studio's detection on the editor's height check). Heights: about 128 x 128 points within half a game unit; a field with less than 2 units between its lowest and highest point says nothing. Markers: each start position and mass or hydrocarbon marker is mapped by every copy and must land on another marker of its kind within about a percent of the map (one on the axis counts neither way). A start without its partner, or more than half the resource markers without theirs, rules a mode out; otherwise 97% of the points matching settles it, and with fewer the markers must prove it (every start paired, three quarters of the resources, and 90% of the points or flat ground), so a flat new map with placed markers is found too. The mode with the most paired markers wins, then on flat ground the fewer copies and otherwise the more, then the closer match. For the mirrors and the half turn an axis a little off the middle is measured from the partners and tried; the Tools panel names the markers that fit and says when the centre is off the middle (Make symmetric then uses that centre; the brushes still mirror about the middle). GPG's own maps place resources only roughly: SCMP_009's half turn pairs all 8 starts and 75 of 116 resource copies, with 98.6% of the points.

**Symmetry check** (Tools panel, Terrain, under Symmetry; `tools/EdSymmetryCheck.cpp`): Check compares every vertex with its copies under the chosen symmetry and marks the differing ones as red blocks on the terrain (Show differences), with a count and the largest difference; it is kept up to date after strokes, undo and redo. N-way turns compare a vertex with the height at its point turned back into the first sector and count differences above a quarter unit. "Copy the source part to the other copies" makes the heights symmetric from the part nearest the map's top-left corner (the first sector for turns), as one undo step. With the Texture tool it compares the masks (above); the props are checked by View > Check (below). `/symcheck <mode>[x<turns>][:repair]` with `/open <map>` runs the check (mode: the panel's symmetry, 0 None to 9 N-way) and the copy on the drawn map (GoogleTest `faf_editor_brush_tests`: a planted one-vertex difference is found and repaired in every mode).

**Make symmetric** (Tools panel, under the symmetry check once it found differences; `tools/EdSymmetrize.cpp`, FAF Studio's `symmetrize` op in the terrain library): the source part (part 1 is the left or top one, the others follow round the centre), how the copies combine (copy the source part, or the average, highest or lowest of every copy), a seam that cross-fades the part's borders into the copies beside them (copy only), and with the Terrain tool the texture masks and the terrain types too (types take a copy's code, never a blend). Heights, masks and types are each one undo step. `/symoptions <part>,<combine>,<seam>,<masks>,<types>` sets them for test runs with `/symcheck <mode>:repair`; on SCMP_009 part 2 with an 8-sample seam took 127,632 differing vertices to none and made its 512 x 512 masks and 1024 x 1024 terrain types symmetric.

**Height field import and export** (Tools panel, Terrain, Height field; `tools/EdHeightFile.cpp`): Import reads `.png`, `.bmp` or `.tif` through the Windows imaging component as 16-bit grey (8-bit images spread over 16 bits), or `.raw` / `.r16` (World Machine) as 16-bit little-endian words, square or of the map's size; it is resampled to the map's size and is one undo step. Export writes `.png` (16-bit grey), `.raw` or `.r16`, at the map's size or 257 to 4097 wide (a rectangular map keeps its proportions). Heights are times the panel's height scale both ways; a word is 1/128 of a game unit, as in the map file. `/heightexport <file>` and `/heightimport <file>` with `/open <map>` do the same from the command line, and `/heightdialog` opens the import dialog (GoogleTest `faf_editor_brush_tests`: every format reads back what it wrote).

**New map** (File > New map, Ctrl+N; `doc/EdNewMap.cpp`): a title, the folder (FAF's `name.v0001`, from the title until edited), skirmish or campaign, 5 to 81 km, 1 to 16 players, the ground's height and an optional sea with its level (deep and abyss 2.5 and 15 below). The document's worker makes the engine's empty map (`CWldMap::MapNew`, 0x00890D40: the default layers, cleared masks) at that height and sea, and writes `<vault>/maps/<folder>/` with the `.scmap` (a 256 x 256 preview, ground green or sea blue, the start positions as dots), `_scenario.lua`, `_save.lua` (start markers `ARMY_1`... in a ring at 35% of the size, the first at the top; one army entry each plus `ARMY_17` and `NEUTRAL_CIVILIAN`) and `_script.lua`. The folder is then mounted at `/maps/<folder>` (`CVFSImpl::MountDirectoryLate`, an engine addition), listed in the Map panel and opened. `/newmap <folder>[,<size 0-4>,<players>,<height>,<sea level or 0>]` does the same from the command line. The sea's water map starts empty (flat shading) until the water tools fill it.

**Props** (Tools panel, Props): a searchable list of every prop blueprint the game's rules have (`GetPropBlueprints`), the chosen one's reclaim mass and energy, scale and LODs under the list, and in Single mode the prop itself under the cursor with its symmetric copies (drawn by the mesh renderer, at the turn the click will use: a random turn is drawn before the click), Single (one at a click), Scatter (props a second at random points inside the brush while the button is held) and Erase (those inside the brush; Shift+click erases in any mode), random turn, the brush's radius and symmetry: each prop gets its symmetric copies, each copy turned as the symmetry carries the cursor's heading. **Select tool**: a click picks the nearest prop (Ctrl adds), a drag moves the selection over the ground, Q and E turn it by 15 degrees, Delete or Edit > Delete selection removes it; selected props are outlined in yellow with the hover outline's shaders (the one under the cursor in amber over that; past 256 selected props the rest get a yellow ring instead, so a box-selected forest doesn't add thousands of meshes; `/hoverprop <prop> /selectprops <n>` selects that prop and its nearest others for test runs). The prop a click would pick is **outlined** in amber (WPE.54, WPE.57): two more instances of its mesh with techniques the editor appends to FAF's `mesh.fx` (`ren_EditorMeshOutline`, set by the editor only; `CD3DEffectTechnique.cpp`, compiled into a cache of its own named by the appended text's hash, checked when the effect loads and left out if it doesn't compile). `EditorOutline` pushes the model's front faces out along their normals by 0.2% of their distance to the camera, so the rim is about the same width on the screen at any zoom, and draws them in the instance's colour after the water with no depth test; `EditorPropOver` (FAF's `NormalMappedAlpha` passes) then draws the prop again over the shell's middle, so only the rim stays. Both draw over what stands in front of the prop, as an editor's highlight does. An inverted hull (back faces) drew nothing on FAF's rocks, which are open domes sunk into the ground, and a depth-tested redraw didn't match the prop's own depth. Props whose shader is alpha-tested ("...Alpha") get the shell cut out by their albedo's alpha. Swaying props (`UndulatingNormalMappedAlpha`, FAF's trees) get a shell and a redraw that sway as FAF's `UndulatingNormalMappedVS` does (`EditorOutlineAlphaSway`, `EditorPropOverSway`), and a hairline rim (0.07% of the distance): every leaf card gets a rim, and at the full width a tree group was painted amber; now its leaves are edged in amber (561 rim samples on SCMP_009's pine group against 934 before, and the same on Vulkan). On SCMP_009 the hovered fieldstone02 had an amber rim round its exact shape (802 rim samples in the capture, none before). `/hoverprop <index or part of a blueprint path>` keeps the cursor on a prop for test runs. The Properties panel's Prop section opens a **prop browser** ("Change to another prop...", WPE.55): a search box and the game's props as picture tiles (only the tiles in view ask for their picture), the prop's own framed in amber; a click makes every selected prop that one where it stands, as one undo step, its model remade at once. `/propswap <part>` (with `/hoverprop`) selects the hovered prop and clicks the browser's first tile for that search, `/propswapundo` undoes it a second later; on SCMP_009 rock05 (prop 29) became pine06_big_groupa and undo made it rock05 again. Every prop edit is one undo step (the whole prop list before and after; the newest 200 are kept). A new or turned prop is saved from a record of its own floats (position, rotation matrix, scale 1) and takes the transform the engine's `CWldProps::Load` reads back from them, so a save and a read give it back bit for bit; a moved prop keeps its rotation floats as read. `/proptool <mode>,<blueprint>`, `/tool <index>` and `/roundtripframes <n>` (the frames `/roundtrip` and `/saveas` wait) serve test runs.

**`_save.lua` and `_script.lua`** (`doc/EdSaveFile.cpp`): the editor keeps both files' text. The master chain's markers and the areas are parsed out of the save (each a name and its properties as written, so properties the editor has no use for survive); writing gives the text back unchanged, or with only a changed block (markers, areas) written anew in the game's layout. All 63 maps of the game parse, each with as many markers as its Lua gives. Save writes the two files beside a vault map when they changed; Save as writes the edited ones into the new folder.

**Decals** (Tools panel, Decals; `tools/EdDecals.cpp`, `tools/EdDecalShape.cpp`): the map's decals are the terrain's decal manager's (the game's own `CDecalManager`), so they draw as the game draws them and save with the terrain. Place mode: a browser of every texture under `/env/*/decals/` (thumbnails on a checkerboard, filtered by name and by type: albedo, normal maps, glow, the type taken from the file's name), a size along and across the heading, a turn (or a random one) and a fade distance (0: the decal works one out from its size, as the game's `AddDecals` does); a click places the decal centred on the cursor with its symmetric copies, turned with the symmetry, and the outline of the decal to come follows the cursor. A decal's position is its corner, not its middle (`CWldTerrainDecal::ComputeCorner`, 0x0089D9C0), so the editor places the corner half of each side back from the click. Select mode: a click picks the topmost decal (the last drawn), Ctrl adds, a drag moves the selection live, Shift+click or Delete removes. Each edit is one undo step (a snapshot of every decal's saved fields; undo makes the missing ones again with their index and destroys the extra ones). On opening, the log names the decals by type and the first one's fields. `/decaltool <texture>[,select]` for test runs. An albedo texture with a `_spec` next to it gets it as the decal's second texture ("With its spec map", on by default), as the game's maps keep them: SCMP_009 has 1,003 normal-map decals with one texture, 949 albedo decals with one and 284 with their `_spec` second. Thumbnails keep the decal's alpha. Path mode: clicks lay the points of a uniform Catmull-Rom curve (through every point); decals follow it end to end, each its length along the curve and its width across, turned with it, the next starting length x (1 - overlap) further on; the view shows the curve to the cursor and the decals to come for every symmetric copy; Enter or Place lays them as one undo step, Backspace drops the last point, Escape clears. In Select mode the move gizmo stands at the selected decals' middle and moves them along an axis or freely.

**Units** (`doc/EdUnits.cpp`): each army's `Units` group in `_save.lua` (groups nested in `INITIAL`, units with type, orders, platoon, Position, Orientation) is read into groups and units and written back as the game's saves write it (the source's line ends; six decimals, a half rounded away from zero as the game's writer did). With `FAF_RETAIL_MAPS` set to the game's maps folder, GoogleTest round-trips all 380 armies of the retail saves (21,971 units) byte for byte. The view draws them with their blueprint's mesh and scale, turned as `CreateUnitHPR` turns Orientation's heading, pitch and roll (`BuildRotationMatrixFromEulerHPR`, then the canonical row converter): SCMP_001's 774. The Units tool (U) picks an army (players and extra armies) and a unit type from the rules (id and name, searchable); Place puts the unit in the army's INITIAL group with its symmetric copies, named UNIT_n after the highest in the map; a player army's copy goes to the army whose start position is nearest its start's copy (SCMP_009's half turn: ARMY_1's to ARMY_2), an army without a start keeps its copies. Select picks, drags live or with the move gizmo, and deletes; each edit is one undo step with the save data. `/unittool <type>,<army>[,select]` for test runs.

**Unit groups** (Tools panel, Units, GROUPS; `doc/EdUnits.cpp`): the army's group tree (INITIAL, WRECKAGE and the groups under them, as `_save.lua` nests them), each with its units' count. A click on a group selects its units; a group is added in the chosen one, renamed (not to a name its parent has), removed (its units and groups go up into its parent, in its place), or given the selected units; each change is one undo step. SCMP_009's civilians sit in a WRECKAGE group (43 units, no INITIAL); a Docks group added in it saves as the game writes groups. `/unitgroup <add|rename|remove|move|select>,<a/b path>[,<name>]` for test runs.

**What becomes of a unit** (Properties, Unit; `doc/EdUnitFate.cpp`, `ui/EdUnitFatePanel.cpp`): a map's units are only data until something creates their group (FAF's `lua/sim/ScenarioUtilities.lua`): as a game starts, each army's `INITIAL` group becomes units (a civilian army's unless the lobby's Civilians option is "removed") and its `WRECKAGE` group becomes wrecks (`CreateWreckageUnit`: the unit made, its wreck put in its place, the unit removed at once); any other group is in a game only when the map's script creates it (`CreateArmyGroup(army, group, wreckage)` and its kin, read from the script: a name written `'Optional_Wreckage_' .. w` matches the groups it starts; a group made as wrecks for one lobby value and as units for another, as DualGap's civilian base, is "either"). Properties show the unit's group, what becomes of it, and its wreck's value as Unit.lua's `CreateWreckageProp` makes it: the build cost times the blueprint's Wreckage MassMult and EnergyMult, the mass times 0.9 / 0.8 / 0.7 / 0.6 for tech 1 / 2 / 3 / experimental (TechCategory, which FAF's Blueprints.lua takes from the categories), both times 0.6 under water; a naval unit without a Wreckage table gets FAF's default one (MassMult 0.9). DualGap's Salem destroyer in `Optional_Wreckage_2`: 1620 mass. For a script's group the **Lobby** row says which lobby option decides it and what each of its values does (`doc/EdGroupOptions.cpp`): the script is read as Lua (comments and long strings skipped), with the `if` / `elseif` / `else`, `for` and `while` blocks around each `CreateArmyGroup` and the calls of the function it is in (a few levels up), and the options it reads (`local x = ScenarioInfo.Options.key or 1`, or `ScenarioInfo.Options.key` itself); every combination of the deciding options' values from the map's `_options.lua` (an option there is `default` as an index into its values, as FAF's lobby reads it) is evaluated, and conditions on anything else (who plays a slot, factions) are "maybe". A name `'Optional_Wreckage_' .. w` in `for w = 2, optional_wreckage` is made on the turn w equals its number. An option the script reads but `_options.lua` doesn't offer is always the script's default, so its groups never appear: DualGap Adaptive v14 has its naval, middle, faction and civilian options commented out, and the panel shows those groups as never in a game, while `Optional_Wreckage_2` reads "Lobby option "Wreckage" (optional_wreckage): "disabled" (default): not created; "T3 wreckage": created as wrecks". In the Properties panel this is one row, **Appears**: a sentence that is also the choice ("When Wreckage = "T3 wreckage" (wreck)", "From the start, as a live unit", "Never: the lobby has no option optional_naval_wreckage" in amber), its tooltip the details above, and "Option..." beside it opening the Adaptive Map window on that option. The choice (`SpawnTargets`) edits it: from the start as a live unit (`INITIAL`) or a wreck (`WRECKAGE`), or any group the script creates for the unit's army, each with the first lobby setting that brings it in (`Wreckage = "T3 wreckage"`) and whether as wrecks or units; a pick moves the selected units of that army into the group (one undo step). A group no setting makes yet is offered with the `_options.lua` change that does, kept only when reading the script again with it shows the group created: the next level of a looped option adds a value after the option's own (their texts and help kept), and an option the script reads but the lobby lacks is written (disabled, then levels); that change is a second undo step. DualGap's destroyer moved to `Optional_Wreckage_3` added "level 2" to Wreckage, and its Lobby row then read "level 2": created as wrecks. The Adaptive panel's script groups show the same lines on hover. `/unitspawn <group>` with `/selectunit` for test runs. Its Wreck box shows the real state: for a unit of the start groups it moves the unit between `INITIAL` and `WRECKAGE` (one undo step); for a script's group it is shown, not changed (the script decides), with "Move to the start groups". A unit that becomes a wreck is drawn with the `<mesh>_wreck` blueprint FAF's Blueprints.lua makes for every unit (the Wreckage shader), as the game's wreck props are. The Props tool's reclaim summary adds the unit wrecks: those from the start and those all of the script's wreck groups would add (DualGap: 10 frigates, 1361 mass, from the start; 54 more, 15394 mass, with the Wreckage option on). `/selectunit <army>,<unit>` for test runs.

**Saving** (`doc/EdMapFile.cpp`, `doc/EdDocument.cpp`):

- **File > Save** (Ctrl+S) writes the opened map's `.scmap` over its file, only when that file is in the vault (`<vault>/maps/...`): maps inside the game's archives or folders have no file of their own to save over and are saved as a new map folder instead. The first save of a session backs all of the map's files up first (see Autosave, recovery and backups).
- **File > Save as new map folder...** asks for a folder name (the next version, `seton.v0002` after `seton.v0001`, is offered) and writes `<vault>/maps/<folder>`: every file of the map's folder, those named after the map renamed to the folder's name without its version, the `.lua` files' paths into the old folder pointed into the new one, and the edited `.scmap`. The game lists it from its next start.
- The vault is the FAF client's (`custom_vault_path` in `fa_path.lua`, which the init file reads and mounts maps from) when this Windows user can write it; else the user's `Documents/My Games/Gas Powered Games/Supreme Commander Forged Alliance`, whose map folders the editor mounts itself at startup when the init file doesn't (`DISK_MountDirectoriesNow`, one rebuild of the file system), so downloads are there after a restart; or `/vault <folder>` on the command line.
- What is written: the file header, the preview image as read (byte for byte), the terrain as the game's own writer saves it (version 60: heights, the ten texture layers, water, decals, masks and the rest), then the props. A prop the editor didn't move keeps its record byte for byte; a moved one is written from its position and rotation with scale 1, which the game ignores. The masks are written with the classic DDS header (`ImageCodec::PreferOwnDds`): the game's Direct3D 9 decoder doesn't read the newer DX10 header. The normal map and the water maps are rebuilt from the terrain, so their bytes differ from the original file's.
- The terrain's images (the normal map, the two stratum masks, the water map) go back as the file had them where what they are made from is as it was at load (`doc/EdImageChunks.cpp`): the normal map when the heights are, the water map when the heights and the sea's levels are, the masks when their texels are; the engine would encode them again into other bytes (its DXT5, and a DDSD_LINEARSIZE header flag the originals don't set). So SCMP_009 saved unedited is byte for byte its original (9636487 bytes, 0 differ, where 35237 differed before), and after a height stroke only the normal and water maps are new.
- `/roundtrip <folder>` (with `/openall` or alone: every map; with `/open <map>`: the drawn map) saves each map under `<folder>`, reads it back, compares heights, water, shader, layers, props and decals, saves again and compares bytes, then closes. All 63 maps of the game come back with the same data, and a second save is byte-identical to the first. `/saveas <folder>` with `/open <map>` saves the drawn map as that new folder and closes.

**Stratum recipes** (the Texture tool's Stratum recipes section; `tools/EdRecipes.cpp`, FAF Studio's recipes.lua): paints the layers with the eight kinds of ground a landscape is made of (grass, dirt, wet ground, sand, rock, dark rock, high rock, snow) from rules built on the mask generator out of the map's own numbers: the land's height percentiles (above the sea when at least 3 % is), its relief (3rd to 99.5th percentile), and noise thresholds read from the noise itself, so "snow covers the top 8 %" or "dirt covers 38 %" hold on any map; edges are wide smooth ramps whose thresholds wobble with fractal noise. Each layer's kind comes from its texture (`EdGroundKind`: name and average colour) and can be corrected per layer (Auto, a kind, or Not used); the base layer's kind takes what the others leave. The kinds are resolved by priority (snow, high rock, dark rock, rock, wet, sand, dirt, grass), each taking its selection of what the ones above left, so the visible weights add up to one; a kind's second layer takes soft noise patches of its region; a kind the style or the map has none of (snow on a flat map, in the desert) has its layer cleared. Every layer is written with the opacity that shows exactly its weight (the weight over what the layers above leave free), in the shader's mask range; a textured layer of no known kind keeps its mask. Eight styles (Natural, Alpine, Desert, Arctic, Rocky, Open valley, Layered, Coast and wetland) set the settings (cliff and rock slope, snow share, high rock start, beach and wet strip widths, dirt share, dark rock, breakup, patch size, crispness, fine grain, variant mix, blend width, seed), which can be changed under Settings. Paint the map is one undo step; the brush's symmetry copies the recipe's layers together from the source part. The result line gives each kind's share. **Erosion paint** (the style of that name; `RecipeErosionSelections`, FAF Studio's erosionpaint.lua) reads the paint off what the water did, as a World Machine or Gaea project does: wear (the `rockiness` op), deposit (`wetness` on flat ground) and flow (drainage) are made from the heights (no erosion run is kept across strokes, so these stand in for one) and cut at a share of the map (worn rock 12 %, sediment 22 %, channels 7 %, settable) with an edge a small share of the mask's range wide, squeezed twice so it is crisp; rock becomes the cliffs by slope plus the worn ground where it leans at all, dirt the sediment on flat ground, wet ground the drainage network, and a kind's second layer takes a band of the same mask instead of noise (the strongest wear, the thickest sediment, the channel core; a third rock the convex steep ground; a second grass the ridge tops), also when the kind is the base layer's. FAF Studio's terrain types and its roughness for the PBR shaders are not here yet. On SCMP_009 Erosion paint took 0.63 s: grass 26 % (its second layer 7 % on the ridge tops), dirt 64 % (its second layer 6 % on the thickest sediment), rock 10 %. `/recipe <style index>` paints in a test run. On SCMP_009 (gravel base read as dirt, two grass layers, rock, dirt) Natural took 0.27 s: grass 31 %, dirt 68 % (the base, including the sea floor), rock 2 %, 465,835 texels.

**Texture library** (the Layers panel): each layer's menu (right-click a row) has, besides choosing a texture, moving it up or down with its mask and clearing, importing or exporting its paint: **Fill its paint** (the whole map, one undo step), **Remove its texture and paint** (the slot emptied at the engine's size 4 and its mask cleared; the Upper layer only loses its texture), its tile **Size** (the normal map keeps its ratio), the **Normal map** size on its own (usually the texture's, so the bumps sit on their colours), and **Optimal tile size** (`tools/EdTexScale.cpp`, FAF Studio's texscale.lua: the largest tile that stays sharp at the closest zoom, the texture's width in pixels over 48.3 screen pixels per unit, rounded to 0.5, at least 20 so the grain doesn't repeat as a pattern, within 4 .. 64; a 1024 px texture 21, 2048 px 42.5; the width read from the DDS header once per texture), which sets both sizes. **Texture sets** (`tools/EdTextureSets.cpp`, FAF Studio's texsets.lua): nine sets (Temperate, Open valley, Desert, Mars, Tropical, Tundra, Lava, Swamp, Geothermal) name candidate textures for the base layer, the Upper layer and each kind of ground; the first the game has is used, at its optimal tile, the Upper layer at a golden-ratio multiple of the base tile near 128 (so their repeats never line up), and only where the shader draws the Upper layer as an overlay. **Map-wide textures** (the Layers panel's Map-wide textures; `tools/EdMapTextures.cpp`, FAF Studio's maptextures.lua; `EditorApp::MakeMapTexture`): what FAF's newer shaders read from a slot whose size is above the map's. The numbered shaders (Terrain250...) take the map's normals in slot 8's normal map (r, g, b the normal's z, a its x) and its lighting in slot 8's albedo (r water depth, g and b ambient occlusion, a the baked sun shadow); TerrainPBR and Terrain301 take both in the Upper slot (r, g the normal's x and z, b water depth, a shadow). Make draws it from the heights through the field library (`normal_map`; `hillshade` shadow averaged over five samples of the sun's disc for soft edges; `occlusion` cavity), with the map's own sun (from its lighting) and sea, at the map's size up to 1024 px, writes `<map>/env/layers/map_lighting.dds` (map_normals.dds, map_normals_lighting.dds) as uncompressed BGRA with mips, and sets the slot to it at the map's size + 1 (one undo step). Each row says whether it is made here and up to date, out of date (the heights changed since; checked once a second against a checksum of the heights), made elsewhere, or not made; the log says when one goes out of date. Clear empties the slot. Export... saves the slot's texture as a .dds; Import... takes a .dds made elsewhere (packed as the shader reads it; only the DDS header is checked), copies it into `<map>/env/layers/` under its own name and sets the slot to it at the map's size + 1, so its row reads "Made elsewhere". A map-wide slot shows no share of the map. Two more kinds are made from the paint and go in the Upper layer's albedo (`MakePaintTexture`, FAF Studio's SpecularChannels / MacroChannels): the **specular** of Terrain001 and Terrain051 (rgb the shine, 0.08 plus 0.8 times what shines: wet ground 1, snow 0.6, plain rock 0.12, the waterline 0.9 within 2.5 units of the sea, fading over 3 more; alpha the sharpness, 0.3 plus 0.45 times the shine; the layers of one kind add up and the strongest kind wins), and the **macrotexture** of TTerrain, TTerrainXP, TTerrainGlow, TTerrainXPExt, Terrain000 and Terrain050 (the colour the paint shows, each layer's average colour times what it shows, made 25 % lighter and darker in broad patches by a fractal noise of 180 units, alpha 0.35). What each layer shows is its mask weight in the shader's range times what the layers above leave free, the base layer showing the rest (`VisibleWeights`); a layer without a texture shows nothing. Each layer's kind of ground (`tools/EdGroundKind.cpp`, FAF Studio's roledetect.lua) comes from its file name's words (longer tokens first, the last word counting a little more, dark and light words moving a rock to dark or high rock, ice and rock together high rock) and its texture's average colour (decoded at 16 x 16), the colour settling plain rock names, grass against sand, and names that say nothing; the log lists the kinds when one is made. Their rows go out of date when the heights, the masks or the layers' textures change. `/mapwide normals|lighting|specular|macro[,clear|,stale|,export=<file>|,make,export=<file>|,import=<file>]` drives it in a test run (`stale` raises the ground right after Make). On a 513 map: Make then a raise logged the out-of-date line; make,export wrote the 1,398,228-byte texture; importing that file into a new map copied it unchanged. On a new TTerrain map the macro (0.1 s, 512 px) came out tan (mean r 0.425, g 0.415, b 0.366, a 0.35) over the sand base, varying by about 14 % in patches; on Terrain001 the specular of a dry sand map 10 units above the sea is a flat 0.08 with sharpness 0.30, and it went out of date when the ground was raised.

**Moving a layer** (the Layers panel: drag a layer onto another, or Move up / Move down from its right-click menu; `tools/EdLayerConvert.cpp` LayerMoveArrangement, MoveLayerMasks; `EdMapScene::MoveLayer`): strata 1 to 8 move with their masks and textures, the ones between shifting one place; a weight keeps its meaning when it lands on a stratum the shader reads remapped. One undo step. `/movelayer from,to[,undo]` moves one in a test run (and undoes it two seconds later).

**Follow symmetry** (the Select tool's Follow symmetry, on by default; `tools/EdSymmetryFollow.cpp`): moving, turning or deleting an object does the same to its mirrored copies. When the edit starts, each selected object's copies are found: the objects of its kind (a prop's blueprint, a marker's type) nearest the images of its place under the toolbar's symmetry (within 1.5 units; a selected object is never another's copy, each copy is taken once). A drag or a gizmo move puts each copy at the image of the new place (on the ground), Q/E gives prop copies the image of the new heading (the heading carried through the symmetry as the prop placement does), Delete takes the copies too, all in the edit's one undo step. Units find their copies by type (a copy may be in another army), decals by texture at their middles (a decal's position is a corner, which a mirror moves to another corner; the copy keeps its own size and heading). A drag of a Shift copy leaves the original's copies where they are. `/followtest props|markers|units|decals` in a test run: on SCMP_009 (half turn) prop 0 moved by (6, 4) put its copy 2556 exactly on the image (653.18, 444.66) and deleting took both (5,182 props to 5,180); Mass 13 did the same with Mass 12 (341 markers to 339). Decal 5225's copy 10400 ended with its middle exactly on the image (478.98, 682.54), 2,236 decals to 2,234; SCMP_009's units have no mirrored pairs, so the test gives the first one (UNIT_63) a copy at its image, then the move put it exactly on the image (528.50, 524.50) and the delete took both (44 units to 42).

**Arrange** (the Select tool's Arrange section, Edit > Arrange, the palette's `arrange.*` commands; `tools/EdArrange.cpp`): the selection of whichever kind is selected lined up, spread or mirrored, as one undo step. Align left, centre or right sets every x to the leftmost, the middle of the leftmost and rightmost, or the rightmost (top, centre and bottom do the same in z, top being the map's top); Distribute X or Z keeps the two outermost and spaces the others evenly in their order (3 or more); Arrange in a circle puts them on a circle about their mean place, its radius their mean distance from it, evenly in their turn round it, the first keeping its angle (3 or more); Snap to grid rounds to every 1, 2, 4 or 8 units; Mirror left-right or top-bottom flips them about the middle of their box, and props take the mirrored heading (their tilt dropped, as Q/E's copies). Props, markers and units are put on the ground (mass and hydrocarbon markers on a cell's middle, as a drag puts them), decals are arranged by their middles and keep their size and heading, units keep their headings, and nothing leaves the map. The buttons are greyed out until something is selected; a selection too small for an op says so under them. `/arrangetest props|markers,<op>[,<step>]` in a test run selects five, arranges, logs the places and undoes: on SCMP_009 the circle put five props 128.5 units from their mean place, Distribute X spaced five mass markers 154 apart (64.5 to 680.5), Align left put them all at 64.5, Snap 8 gave multiples of 8, and each undo took it back. Arrange doesn't follow symmetry: a mirrored copy keeps its place.

**Find and replace objects** (Edit > Find and replace objects..., Ctrl+F; `tools/EdFindReplace.cpp`, `EditorApp::DrawFind`): Find lists every marker type, unit blueprint, prop blueprint and decal texture on the map with how many there are (kinds in that order, the most first); In is the whole map, the selection, or the symmetry's first part (the toolbar's symmetry: of each set of mirrored copies the one no image comes before, by x then z, so exactly one of each set); Replace with is (delete) or another type of the kind. Select matches makes them the selection; Delete all and Replace all are one undo step, and a replaced object keeps its place, turn and scale (props as Change to another prop does; units their army and name; markers take the new type's properties and keep their name, turn and path links; decals take the other texture's normal map and kind). A decal is replaced only by one of its kind (albedo by albedo, normals by normals), and start positions can only be selected. Delete takes exactly the matches, without follow symmetry. `/findtest kind,<part of the type>,map|selection|half,select|delete|<part of the other type>` runs one and undoes it; on SCMP_009: 1,760 pine06_groupa props became pine06_big_groupa (1,678 to 3,438), 338 erosion018d_normals decals became erosion018_normals (116 to 454), the first part's 54 of the 108 mass markers were deleted, 20 land path nodes became amphibious ones (32 to 52), and each undo put them back. `/findopen <n>` opens the dialog on the n-th type.

**Cut** (Edit > Cut, Ctrl+X): the selection copied, then exactly it deleted (not its mirrored copies, which the clipboard doesn't hold), as its own undo step; Paste at the cursor puts it back anywhere. `/command edit.cut` on SCMP_009 with five props selected: "5 copied", 5,182 props to 5,177.

**Fill the map** (the Props tool, Scatter mode, Fill the map; `tools/EdScatter.cpp`, `EdMapScene::ScatterOverMap`): props from the paint list (by chance, turn and scale, as Scatter does), or the chosen prop, over the playable area: a density per 100 x 100 units, at least a spacing apart, on slopes up to a limit, and only above the water if asked. One candidate is drawn in each spacing-sized cell, kept with the density's chance and dropped when nearer than the spacing to one kept already; only points in the symmetry's first part are drawn, and each is placed with its mirrored copies (a point whose own copy would stand nearer than the spacing, by a mirror line, is left out), so every copy matches. One undo step, a new seed each time; the note under the button says how many were placed and why the others were left out. `/filltest <density>,<spacing>[,keep]` fills with the map's commonest prop, checks the copies and undoes: on SCMP_009 (half turn) 10 per 100 x 100, 6 apart placed 352 props (176 points and their copies; 302 left out under water, 21 too steep), all 176 with their copy, and undo put back 5,182; 30 per 100 x 100 placed 1,106.

**G and R** (the Select tool; `tools/EdModalTransform.cpp`, `EdMapScene::BeginModal`): with something selected, G makes it follow the cursor and R turns it about its middle, until a left click or Enter keeps it or Escape or a right click puts it back (kept as one undo step, then undone, so everything it touched goes back exactly, mirrored copies too). X or Z locks the move to that axis, drawn across the map in the gizmo's colour (X again unlocks); a typed number (digits, '.', '-' flips the sign, Backspace) moves exactly that far, along X unless Z is locked, or turns that many degrees. While it runs the view takes every key (digits aren't the tools' keys then), each moved thing's old place stays drawn with a dashed line to the new one, and the HUD says what it is doing ("Move along X (typed) 40.00"). Props and units turn with their headings (a unit's is its Orientation y), markers and decals keep theirs (decals move by their middles), mass and hydrocarbon markers land on a cell's middle, and follow symmetry moves the mirrored copies. `/modaltest props|markers|units,g|r,<keys>[,cancel|hold]` begins one on five selected, types the keys and ends it: on SCMP_009 G x12 moved the first prop from 364.82 to 376.82 in x, R 90 turned a prop from 169 to 259 degrees about the five's middle, G z-8 then Escape put a mass marker back at 678.50, R 45 turned a unit from 18 to 63 degrees, and hold left G x40 running for a picture (the axis line, the ghosts, the HUD).

**Looks** (the Lighting panel's first section; `doc/EdLooks.cpp`, `EditorApp::UpdateLooks`): every map the game lists is a look, and so is each look saved in the editor's Looks folder (`%LOCALAPPDATA%\FAForever\Editor\Looks`, FAForeverMapEditor's `.scmlighting`, `.scmwtr` and `.scmskybox` under one name). A map's look is read from its `.scmap` through the game's files (archives too) when it is first tried: the environment cube lookups, the lighting, the water (CWaterShaderProperties::Load's numbers, cubemap, ramp and the four wave normal maps) and, walking past the wave generators, palette, texturing, decals, masks and terrain types as the loader does, the sky (SkyDome::Load, from format 0x3A). A click tries it on the open map (Try on click; no undo step), Apply keeps it as one undo step (the look edit kind: lighting, water and sky together), Revert takes it off. The ticks choose Lighting, Water (colours, reflections, sun, cubemap and ramp), Waves (the normal maps) and Sky; Blend mixes the numbers with the map's own and switches names, counts and planets at one half; the water's levels are never taken. Each row gets four swatches (sky horizon and zenith, sun, water) once read. Save look keeps the open map's own look under a name, and a saving of the map while a look is tried writes the map's own look and puts the tried one back. `/looktest <map folder>,<sections>,<blend>,apply|revert|keep` (or `mine:<name>`, or `save:<name>`; `/looksfolder <dir>` moves the Looks folder) runs one: on SCMP_009, SCMP_001's look applied changed the multiplier 1.54 to 1.40 and the water colour 0.00 0.70 1.50 to 0.06 0.09 0.00 as one "look" step that undo took back; lighting only at blend 0.5 gave 1.47 and Revert 1.54; the sky alone from X1MP_002 gave 5 planets and horizon 0.56 0.67 0.72 (SCMP_015's: none and 0.70 0.60 0.50); SCMP_015's own look saved and tried on SCMP_009 gave its 1.60, 0.70 0.60 0.50 and no planets. Saving a map while a look is tried wasn't run (it would write a retail map).

**The water's sun** (the Water tool, Sun on the water): its direction is shown as an azimuth and elevation of where the sun is, as the Lighting panel shows its sun, and its Strength (CWaterShaderProperties' SunStrength) has a slider. The water keeps the way the light travels (every retail map has 0.1, -0.963, 0.252, nearly straight down, whatever its lighting), the opposite of the lighting's "towards the sun" vector. Follow the lighting sun (on by default) makes a turn of the sun in the Lighting panel set the water's sun to the light's direction too, in the same undo step (an "environment" step); opening a map never changes it. Unlinked, Take it now copies it once as a water step. Typing azimuth 120 into the Lighting panel on SCMP_009 (a double-click on the slider, through the panel's own input) gave the sun -0.415 0.559 0.718 and the water's 0.415 -0.559 -0.718 as one environment step.

**Sky and reflection cubes** (the Lighting panel's Sky and Reflection cubes sections): the sky is edited as the map keeps it (SkyDome): horizon and zenith colours, the dome's size, horizon and zenith heights, how far it is lowered, its segments round and up, the planets' glow, the cirrus colour, strength, texture and four layers (frequency, speed, direction), and each planet's place, turn and size or its removal; each edit is one sky undo step. The reflection cubes are the map's environment lookups (CWldTerrainRes's Enumerate/Add/Remove/ClearEnvLookup): a name in angle brackets (`<default>`, `<aeon>`, `<seraphim>`) and the cube map units and the water reflect; a path changed, a lookup added (a bare name gets its brackets) or removed is one environment step, and a map without `<default>` is offered it back. Looks carry the cubes with the sky. `/envtest cubes|sky` runs one edit and its undo: on SCMP_009 a fourth lookup came and went, and the sky's horizon turned 1.00 0.20 0.10 with 8 of its 9 planets, then back. View > World groups the Lighting panel and the Water tool.

**Water masks** (the Water tool's Water masks section; `tools/EdWaterMasks.cpp`, `EdMapScene::DabWaterMask`): the map keeps three masks at half its resolution (a byte for every 2 x 2 units; CWldTerrainRes::GetWaterFoam, GetWaterFlatness, GetWaterDepthBias). Foam (0, the default, to 255) and flatness (255, the default, the waves at full; 0 calm) are packed into the water map the water shader reads (RebuildWaterMapRect: foam in alpha, flatness in red); depth bias (127) is loaded and saved but nothing draws with it. With Paint in the view on, a drag paints the chosen mask towards a value, with a radius, strength and falloff (each dab moves a cell at least one step, so a weak brush still finishes) and the symmetry's copies, and the water map is rebuilt where it passed; each stroke is one undo step ("water masks"). While painting, the mask shows over the ground where it isn't at its default, in eight bands (foam white, flatness blue, depth bias amber). `/watermasktest foam|flatness|bias,<value>,<radius>[,keep]` paints a three-dab stroke: on SCMP_009 (half turn, 512 x 512 masks) foam to 255 at radius 40 changed 4,084 cells (the stroke and its copy) as one step, and undo put all of them back; a calm stroke left kept shows two mirrored patches in the overlay.

**Smooth lake shores** (the engine's `ren_WaterHiRes`, `docs/SWITCHES.md`; the editor sets it to 2 at startup, `/nowaterhires` keeps the map's own): the map's water map has a texel for every 2 x 2 cells and its shore flag is "a corner of the four is land", so a lake's edge is drawn as 2-unit steps. With the setting on, the terrain and water renderers get a second water map with that many texels a cell, each reading the ground's bilinear height and its own water's level (the sea or its water body); the saved map, the masks and the sim are untouched, and the game keeps it off. On SCMP_009's steep shore at (806, 400) the steps along the right-hand cliff became a smooth waterline (other steps there are the same with it off, so they aren't the water map's). It is 2048 x 2048 on a 20 km map, built in about 20 ms; an edit's refresh comes at most every 100 ms, a brush stroke's in 2.5 ms plus 5 to 12 ms to hand the whole texture to the GPU, and a sea level change refreshes all of it (`/envtest level`: 16 ms plus 11 ms). `/camat x,z,distance` puts a test run's camera over a point.

**Brush tiles, falloff curve, map counts** (the concept's Terrain tool and Properties): the fifteen brush modes are bordered tiles with the mode's icon above its name (`ModeTile(icon, label, ...)` in `ui/EdControls.cpp`, the editor's own icon font), the picked one in the accent; under the radius, strength and falloff sliders a curve shows the brush's strength across its middle, drawn from `BrushWeightAt` (so a shape and its turn show too) over quarter lines; and Properties with nothing selected shows the map's markers, props, units and decals as four number cards, counted each frame by the view (SCMP_009: 341, 5,182, 43, 2,236).

**Erosion window** (Terrain > Erosion..., or the Terrain tool's Erosion... button; `tools/EdErosionSuite.cpp`, `EdMapScene::RunErosion`): the field library's three solvers (terrain/EdErosion.cpp: hydraulic grid, droplets, stream power), each with its settings and the ones they share (hardness and rain variation, protect ridges, keep height range, largest change, keep volume), as FAF Studio's erosion.lua lists them, and its six presets (Mountain, Hills, Canyon, Alpine, Desert, River valley). Preview runs on every few samples (the smallest step keeping 257 a side, one that divides the map when it can; 4 on a 20 km map) with the settings scaled to match (iterations, rain, rates, droplet life, radius and density) and adds the change it made, upsampled, to the full heights, so the fine detail stays; the preview is an ordinary undo step, and Revert undoes it while it is still the newest edit. Apply takes a shown preview off, then runs at full resolution as one undo step. `/erosiontest <preset>` runs Preview, Revert, Apply and Undo a second apart and logs a checksum of the heights: on SCMP_009 with Hills the preview (0.2 s) changed 1,040,856 samples, Revert gave the original checksum back exactly, Apply (1.5 s) changed 1,037,993, and undo took it back. Masks to layers: Wear (where ground was worn away), Deposit (where sediment settled), Flow (where water ran) and Rivers (the drainage: where rivers gather) each go into a chosen texture layer on Apply, scaled to 0..1 as Studio does (over the mean plus three deviations, then a curve of 0.7 for wear and deposit and 0.5 for flow; the drainage is the solver's own) and sampled over the mask grid, with the heights as one undo step ("heights and texture masks", taking both back). `/erosiontest hills,masks` painted wear into layer 5 and deposit into layer 6 on SCMP_009, and one undo gave both the heights' and the masks' checksums back. The GPU solver comes later.

**SC tools** (Terrain > SC tools..., or the Terrain tool's button; `tools/EdScTools.cpp`, `EdMapScene::RunScTool`), after FAF Studio's sctools.lua over the field library's ops (terrain/EdFieldSc.cpp):
- Base pads and resource rings: every start (`ARMY_n`), mass and hydrocarbon marker gets a pad, flat over its half-width and blending into the ground over its skirt (pad_flatten, quantised to a height word). Mass and hydrocarbons within the ring radius of a start share its pad's height; other close resources of one kind share one height per cluster; the pad height is the mean, lowest or highest of its core. Applying again takes the last pads off first (their change is kept), so moved markers get moved pads, and Remove takes them off; each is one undo step, and pads whose step was undone are forgotten. Auto re-applies half a second after the markers stopped moving (not while one is dragged, and not with redo steps waiting). The markers' saved heights aren't changed.
- Slope limit: the steepest neighbour difference clamped to the rating land units can cross (0.75), lowering the high side, raising the low side or both, with balance, margin and strength (slope_limit); Report gives each unit class's blocked share (its slope rating over the limit for a 1, 2, 3 and 5 cell footprint), before and after an apply.
- Ramp check: the grade along the ruler (Alt+drag), sampled every unit as the rise over 3 units, with its length, height range, steepest and mean grade, the share over the limit and each stretch over it.
`/sctest` presses the buttons in turn with a checksum of the heights: on SCMP_009 the pads were 124 (11 shared heights) and changed 15,448 samples, applying again changed none, Remove gave the original checksum back; the slope limit took the blocked ground from 2.6, 3.4, 4.2 and 5.6% to 0% (61,632 samples) and undo restored the checksum; the ramp check over a 64-unit ruler found a steepest grade of 2.25 and 34% over the limit.

**Import / Export window** (Terrain > Import / Export...; `tools/EdInterop.cpp`, `EdMapScene::RunInterop`), after FAF Studio's interop.lua:
- Import: a 16-bit PNG, TIFF or `.raw` / `.r16` file, resampled to the map. Its values are either stretched from darkest to brightest over a height range or read as heights (1/128 unit a step) times a scale. It can be flipped either way, turned in quarter turns, and replace the heights, add to them (its lowest point adds nothing), keep the higher or the lower, at a strength. Probe reads the file and says its size and what its values become next to the map's range; Import is one undo step, and Revert undoes it while nothing was edited after it.
- Live link: with the box ticked, the file's size and time are checked four times a second, and a second after another tool saved it, it is imported again with the same settings. While the last link import is still the newest step it is undone first, so the history keeps one step for the whole session with the other tool.
- Export: the heights at the map's size or 257 to 4097 samples, times a scale, with a sidecar `<file>.json` holding the map's name and size, the image's size, the height per value, the lowest and highest heights, the sea level and the symmetry. Send and watch exports and then links the same file back in as heights (no turn, no blend, the export's scale undone), for a round trip through another tool.
`/interoptest <folder>` runs the buttons in turn with the heights' checksum and writes its files in that folder only: on SCMP_009 the export wrote a 1025 x 1025 PNG and a 306-byte sidecar; a square of the linked file raised by 10 units came in as one undo step (10,000 samples), a second save replaced it (still one step), and undo gave the original checksum back; a stretched, flipped, turned Keep-the-higher import changed 773,779 samples and Revert gave the original checksum back.

## How it is built

- **Target:** `src/editor/CMakeLists.txt` adds `faf_editor`, which links the engine's object library `faf_engine` whole, as the engine tests do, so the engine's objects are linked in the game's order. The game's `WinMain` is one of them, so the editor starts at its own `main()` (`/ENTRY:mainCRTStartup`). It carries the game's window resources and manifest and the DXC DLLs as the game does.
- **The game inside:** the editor's app (`EdApp.cpp`) holds the game's own `CScApp` and runs the game's loop (`WIN_AppExecute`), with what the game's `WinMain` sets up around it (the crash report's die handler, the accessibility hotkeys turned off and restored). The window, device, user interface, sound and world sessions are the game's, unchanged. Engine additions in `CScApp`, unused by the game: `moho::gAppRenderers` (Direct3D 12 and Vulkan only, no Direct3D 9/10 fallback), `moho::gAppWindowed` (one normal window; `SC_PrimaryAdapter` leaves it alone) and `moho::gAppBeforeDeviceCreate` (the editor's second head). The game's first-frame start (main menu or command-line session) is skipped; sessions start from Play.
- **Two heads:** the device has the game's head 0 on the game's viewport, which the editor keeps over the middle of its dock layout, and a head 1 on the editor's own child window under it, for the panels. The game draws only head 0 (its viewport was made for one head); the editor draws head 1 each frame, and the game's paint presents both. When the layout or the window changes, the viewport is moved and both heads are resized (`CD3DDevice::InitContext`). The game's interface lays itself out in the viewport, as in the game.
- **One picture:** the game's view is shown inside the panels' picture, not through its own window: before the panels draw, head 0's back buffer (the frame the game drew last, not yet presented: `CD3DDevice::Paint` presents, then draws the next) is copied with `StretchRect` into a target of the view's size, and the panels draw it under all their windows. The viewport's window keeps its place with an empty region, and the panels' window hands it the mouse (in its own coordinates), the cursor and, on a click, the keyboard wherever no popup or floating window covers it. So popups, tooltips and floating windows over the view move with it in one picture; through the window's own picture they lagged a frame or two behind. `/nocomposite` shows the view's window again, with holes cut where popups reach over it.
- **Panels:** [Dear ImGui](https://github.com/ocornut/imgui) 1.92.4, docking branch, pinned in `cmake/FafDependencies.cmake` and built by `cmake/deps/imgui`, drawn by `ui/EdImGuiRenderer.cpp` on gal's GPU programs (`gpg/gal/GpuDriven.h`): one HLSL source DXC builds for both APIs. Its input is the panels' window's; F5 is the editor's in either window.
- **Play** (`EdPlay.cpp`): the editor's Lua launcher builds the session info as FAF's quick start does and calls `LaunchSinglePlayerSession`; `WLD_Teardown` ends the session, before the game's frame would go on to its main menu. A Lua request to quit during play (`ExitApplication`) ends the session, not the editor.
- **Older renderers:** their DLLs are delay-loaded (`d3d9.dll`, `d3dx9_43.dll`, `d3d10.dll`, `d3d11.dll`), so the editor starts without the June 2010 DirectX runtime and never loads Direct3D 9. Direct3D 11 still loads when Direct3D 12 or Vulkan decode a texture: they do it on a private WARP device ([Renderer backends](RENDERER_BACKENDS.md)).
- **Terrain field library** (`terrain/EdField*.cpp`, from the FAF Studio fork, namespace `faf::editor::field`): float grids with a world placement and pure ops on them by name (`RunOp`): noise (perlin, simplex, ridged, billow, voronoi, cells, musgrave, craters, dunes, cracks, island), filters (blur, bilateral, diffuse, unsharp, morph, convolve, warps), analysis masks (slope, curvature, aspect, flow, distance, shore, occlusion, wetness), the Generate ops (fractal, amplitude, terrain_mix, keep_side), Supreme Commander ops (pad_flatten, symmetrize, slope_limit, reach, regions), path ops and the interop resamplers. It uses no engine type. Each output sample depends only on its inputs, and sums combine fixed row chunks in order, so a result is the same to the bit for any number of threads. Its own small pool runs the rows, and the files turn off fused multiply-add. `faf_editor_field_tests` checks the 82 golden checksums of Studio's cases file (`tests/editor/data/field_cases.lua`) at 1, 2, 3, 5 and 8 threads, plus the ops' properties. The erosion files (`EdErosion.cpp`: hydraulic, droplet, stream power, slope-area, basin depth and the brush session; `EdFieldEro2.cpp`: rock and soil, snow, wind, glacier, thermal map, settle) pass their 34 golden checksums and Studio's property, border and brush tests (`tests/editor/ErosionTests.cpp`). Water erode keeps the editor's own droplets: Studio's brush lets part of the sediment run away, and Water erode moves ground without losing any (`WaterErodeCarvesARampWithoutMakingGround`).
- **Look** (`ui/EdThemeStyle.cpp`, `ui/EdControls.cpp`; the mockup's `styles.css`): every theme starts from the mockup's palette (window, docks and inputs, panels, raised and pressed surfaces, lines, four text greys) with 1 px borders round frames, 4 px rounding and rows a little taller than ImGui's, the Lua themes' colours over it; the default theme is FAF Blue (the mockup's blue accent; Editor Dark, the old orange one, is still in View > Theme). Sliders and drags are fill sliders: a dark track with the value as an accent fill, the name on the left and the value on the right, a drag anywhere scrubs (Shift fine), a double-click or Ctrl+click types a number; buttons are raised with a border, a panel's main action filled with the accent; segmented choices sit in a bordered track with the chosen one filled; the terrain brush modes are bordered tiles. Dropdowns are the mockup's selects (`EdBeginCombo`, `EdCombo` in `ui/EdControls.cpp`, used by every dropdown): the field with its value and a small chevron, where ImGui draws a button-coloured box with a white triangle. Panels are in folding sections (a chevron and a small capitals title; the open state is kept per section), rows put their label in the left 38% and the control beside it, and colours are a swatch (a click opens the picker) with the hex beside it; a colour that may be brighter than white (sun, ambient, shadow, specular) shows a Brightness row once it is, and its picker sets the brightness. The Lighting panel follows the mockup: Sun (azimuth, elevation, multiplier, colour), Ambient and shadow, then Specular, Bloom and fog and the rest folded. The title row's menu labels sit on the row's middle with the workspace tabs and the title (the menu bar drew its text a frame padding below), spaced so a lit label's box (round its text, the tabs' height) never reaches a neighbour, and their popups are padded with taller rows (they took the row's zero padding before); the app's mark at the left of the row is a button that opens the start screen. The workspace tabs carry their icons, the shown one in the accent's soft fill and colour, with rules between the groups (making the map, its assets, Review); a tab's tooltip names the workspace, its keys and what it is for ("Layout workspace · Alt+4"). Panel tabs carry their icons too; a tab's close button shows on hover and the panel menu sits at the tab row's right end. Layouts saved before the tabs had icons keep their places: the first workspace's windows were named by their bare titles, and their saved places go to the new names at the first frame (`EdShell::CarryPanelPlaces`).
- **Icons** (`ui/EdIconFont.h`, `tools/editor/icon_font/`): the mockup's 104 line icons as a font of our own, merged into the panels' font so any label can carry one (`ICON_UNDO " Undo"`), at about 1.1 em. `icons.txt` lists them as SVG (24 x 24, stroked 1.7 wide with round ends); `make_icon_font.py` (fontTools and skia-pathops) turns the strokes into outlines and writes `ui/EdIconFont.cpp` (the embedded TrueType) and `ui/EdIconFont.h` (a UTF-8 string per icon, U+E000 on). After changing `icons.txt`, run it again; `--ttf <file>` also writes the font to look at.

## Known issues

- Each Play still keeps a little private memory after it ends: over 20 plays of SCMP_009 on Direct3D 12 the lowest point after a play rose 1248 to 1380 MB, 82 MB of it the first play's warm-up, then about 1.9 MB a play, 0.7 MB over the last ten (it was 15 MB a play). The heap, the Lua range and the GPU's memory stay flat once warm; what grows is in the graphics driver's write-combined blocks. Freed before: a sync packet's shared references (the sim's height field, 4 MB), the world meshes the game UI never destroys, the cursor each UI state switch made, the Lua range's unmerged free blocks, the particle buffers a play first used (FAF's 4096-buffer pool was handed out oldest first), and the UI Lua state's garbage, now collected after each play.
- The editor started by a tool that can't reach the desktop's browser (Windows reports no association) can't open FAF's sign-in page; the card shows the link to copy instead.
