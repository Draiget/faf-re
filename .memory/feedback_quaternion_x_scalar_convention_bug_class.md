## The bug class

`Wm3::Quaternion<float>`'s real memory layout (`dependencies/WildMagic3p8/Foundation/Math/Wm3Quaternion.h`, ~line 150) is a union of `Real m_afTuple[4]` and `struct{Real w; Real x; Real y; Real z;}` — so `.w` is storage slot 0, `.x` slot 1, `.y` slot 2, `.z` slot 3. WildMagic's own native code (`Quaternion::ToMat3`, `Slerp`, etc.) treats `.w` as the scalar/real component — standard textbook convention.

But large parts of THIS ENGINE's own quaternion-producing code uses a different, non-standard convention: **`.x` is the scalar lane**, and `.y/.z/.w` are the three imaginary lanes, in that cyclic order. Confirmed independently, term-by-term against ground truth `.c` disassembly, in: `Moho::VMatrix4::Set` (0x004EE980), `Moho::QuatToMatrix` (0x00452FD0), `Moho::MultQuadVec` (0x00452D40, the correct rotation helper — used ~20+ places engine-wide, always correctly), `Moho::QuatCrossAdd` (0x0044F880).

`Wm3::MultiplyQuaternionVector` (a "FAF MOD" free function added in `dependencies/patches/wildmagic3p8_faf_required.patch`, calls `quat.ToMat3()`) assumes `.w`-scalar. When an engine `.x`-scalar quaternion gets fed into it, the rotation is NOT subtly wrong — it's a materially different, generally-garbage rotation (the "scalar" and one "vector" lane are swapped in the underlying math).

## Fixed instances (2026-09-01, commits on `master`)

- `VTransform::Apply`/`Compose`/`Inverse` (VTransform.cpp) — all three used `Wm3::MultiplyQuaternionVector` where ground truth (`FUN_00491200.c`, `FUN_00549C20.c`, `FUN_0046FBF0.c`) uses `Moho::MultQuadVec`. `Compose`'s quaternion-multiply formula also had every output lane cyclically mislabeled (computed the right term SET, wrote each result to the wrong field) — a `.w`-scalar Hamilton product instead of `.x`-scalar.
- `Moho::QuatCrossAdd` (Sim.cpp) — wrote its dot-product (scalar) term to `.w` and the three cross-product terms to `.x/.y/.z`; ground truth (`FUN_0044F880.c`) writes dot→`.x`, cross→`.y/.z/.w`. High-impact: every caller feeds the result into `MultQuadVec`.
- `QuatFromVecRot` (QuaternionMath.cpp, used by `Moho::Projectile::MotionTick`/`UpdateTracking` — projectile homing) — same `.w`-vs-`.x` mismatch in its forward-axis column extraction and final Hamilton product.
- `CAimManipulator::CheckTracking` — same pattern (found by a dispatched background agent auditing the remaining call sites).

## Critical false-positive found while hunting this — do not pattern-match blindly

`RotateQuatByAngle` (QuaternionMath.cpp, 0x004EB740) superficially looks like the same bug (reads `.x/.y/.z` as a 3-axis, `.w` for a hemisphere-sign check) — but ground truth proves it's **correct as-is**. It's a general "build a small-angle rotation around MY OWN axis" utility that reconstructs the whole quaternion from scratch via `cos`/`sin`, and it always writes its OUTPUT in `.w`-scalar layout regardless of what convention fed it in. Its existing recovered C++ already matched ground truth exactly.

Worse: in `QuatFromVecRot`, `RotateQuatByAngle` runs on `delta` (a `QuatCrossAdd` output, genuinely `.x`-scalar) and rewrites it to `.w`-scalar — so the SAME variable is `.x`-scalar before that call and `.w`-scalar after it, and the final Hamilton product genuinely combines one `.x`-scalar operand with one `.w`-scalar operand. This is not an inconsistency in the recovery — it's a real, faithfully-reproducible quirk of the original 2007 binary. The fix was to transcribe each field literally per its own ground-truth term (not assume either operand's convention), which reproduces the binary's mixed-convention result exactly. **Do not "fix" what looks like a convention mismatch without checking that specific function's own ground truth — some functions genuinely produce/consume the "other" convention on purpose (or by an original, faithfully-reproducible bug), and a convention-purity "fix" would itself be a new deviation from the binary.**

One IDA-decompiled-C gotcha hit while chasing this: the `.c` pseudocode for `QuatFromVecRot`'s call to `RotateQuatByAngle` read `fun_RotateQuat(&a1a.x, rads)`, which looks like it passes the address of just the `.x` field — but the raw `.asm` (`lea ebx, [esp+4Ch+a1]; dest` then `mov esi, ebx` right before the call) proves it's actually the address of the whole struct. IDA's pseudocode field-name rendering can be wrong; when a pointer's target field identity matters, check the `.asm` directly rather than trusting the `.c` label.

## How to audit a new call site

1. Find the enclosing recovered function's `Address:` comment, read `decomp/recovery/disasm/fa_full_2026_03_26/FUN_<addr>.c`.
2. Identify what the ground truth ACTUALLY calls at that point (`Moho::MultQuadVec`? a different helper? nothing, because the quaternion is genuinely WildMagic-native)?
3. Trace where the quaternion argument itself comes from — a `VTransform::orient_`/similar engine field (almost certainly `.x`-scalar), or a locally-built WildMagic-native quaternion (e.g. via `FromAxisAngle`) that never touches engine `.x`-scalar code (then `Wm3::MultiplyQuaternionVector` is correct, leave it alone).
4. If ambiguous from the `.c` alone (pointer/offset identity, or a function that visibly rewrites its argument from scratch like `RotateQuatByAngle`), check the raw `.asm`.

## A THIRD form: hand-inlined Hamilton product, no named function call at all (found + fixed 2026-09-01)

`HardwareMeshBatch.cpp`'s `FillInstanceBonePalettes` (GPU skinning palette fill, inlined into `HardwareMeshBatch::Func9`/`FillBatch` at 0x007E7EA0 in the binary) composed `composite.orient_ * restRotation` by hand-writing the textbook `.w`-scalar Hamilton product term-by-term — no call to `Multiply()`, `Rotate()`, or `MultiplyQuaternionVector` at all, so NEITHER of the two greps above would ever find this. Fixed in `96a0f050`.

This one was genuinely hard to derive: `restRotation`'s four components are read in the ground truth (`FUN_007E7EA0.c`) as four RAW floats off `SAniSkelBone::mBoneTransform.orient_`'s memory layout (`v61..v64`, matching the struct's declared `(w,x,y,z)` storage order per `VTransform.h`'s own comment), NOT matched named-field-to-named-field against `composite.orient_`'s named fields. The result does NOT show the "same-named-field-paired" pattern every other formula in this bug class has shown (e.g. `VTransform::Compose`'s `a.x*b.x - a.y*b.y - ...`) — instead `c.x` pairs with `b.w` (one position back in the `x→y→z→w` semantic cycle), because `b`'s values are read in raw memory order while `c`'s are read by name. Don't expect a "clean" pattern when one operand's fields come from a raw offset read and the other's from named access — verify by re-deriving term-by-term AND cross-checking with concrete numeric substitution (pick arbitrary numbers for both operands, evaluate both the ground-truth expression and your rewritten one, confirm they match) rather than trying to eyeball whether the formula "looks right."

**If continuing this bug hunt**: grep for other hand-inlined quaternion-multiply shapes (four `float`-returning expressions each summing ~4 products of two 4-component structs, no named `Multiply`/`Rotate`/`MultiplyQuaternionVector` call) — these won't show up in a function-name search. `HardwareMeshBatch.cpp` was found by chance (reading a comment that said "Hamilton product... written in the binary's exact grouping") while investigating something else, not by systematic search. `grep -rn -B3 "NormalizeQuatInPlace" src/sdk --include=*.cpp` is a decent (if noisy) heuristic — composition is usually followed by a renormalize in this codebase, though most hits are LERP/Slerp blends (safe, convention-independent, don't touch) not Hamilton products.

## Full WildMagic Quaternion API surface swept (2026-09-01) — this is believed complete

Checked every quaternion operation that could plausibly carry the `.w`-vs-`.x` scalar assumption:
- `ToRotationMatrix`/`.ToMat3(`/`ToAxisAngle`/`::Slerp` (direct calls): only 2 hits, both in Lua round-trip marshaling (`SCR_Math.cpp`) where input and output go through the same convention — self-consistent, safe, not touched.
- `.Align(`/`->Align(`/`FromRotationMatrix`/`::Exp(`/`::Log(`: **zero hits anywhere in `src/sdk`** (the one `::Log(` match is `Sim::Log`, unrelated).
- `operator+`/`operator-`/scalar `operator*(Real)`: component-wise or uniform-scale, convention-independent by construction, not a risk, not checked further.

So the known-complete list of risky operations is: `Wm3::MultiplyQuaternionVector` (free fn, swept 20/20), `Quaternion::Rotate(vector)`, `Quaternion::Multiply(a,b)`, `Quaternion::operator*(const Quaternion&)` (infix, same bug as `Multiply` — confirmed via `Wm3Quaternion.inl:186`, `m_afTuple[0]` gets the same dot-product-shape scalar term), and hand-inlined Hamilton products (only one found: `HardwareMeshBatch.cpp`, fixed). If a future session finds MORE convention bugs in this codebase, they're likely hiding in one of these four shapes, or in a hand-inlined pattern the `NormalizeQuatInPlace`-proximity heuristic didn't happen to catch.

**A genuine additional bug found while verifying this pass, unrelated to the .x/.w convention itself**: `Moho::VAxes3`'s quaternion constructor (`MathReflection.cpp`, `VAxes3::VAxes3(const Wm3::Quaternionf&)`) did not match its own ground truth (`FUN_004EC590.c`) AT ALL — not a convention mismatch, a genuinely different, wrong computation (proven by direct numeric substitution: same input gave `vX.x=-49` in ground truth vs. `-25` in the old code). This was a **pre-existing bug**, not introduced by the audit pass. Fixed in `89b504e4` — the correct formula is exactly `VMatrix4::Set`'s rotation block, row by row (`vX=r[0]`, `vY=r[1]`, `vZ=r[2]`). `VAxes3` is used in **17 files** (AI, animation, effects, physics, mesh, terrain, units) — this one fix corrects every orientation-derived basis that goes through it.

The audit agent had independently discovered a symptom of this same bug (comparing old-broken-`VAxes3` output against a `MultQuadVec`-based substitute, in `SPhysBench::GetImpulse` and 3 other sites it touched) and misdiagnosed the cause as "`VAxes3`'s `vX`/`vY`/`vZ` are a permuted, partially-negated readout of the rotation matrix, not the plain rows" — written into 4 call-site doc comments as a "verified numerically" fact. It is NOT true (proven false once the real bug was found and fixed): `VAxes3`'s members are simply the plain rotation matrix rows, numerically identical to what `MultQuadVec` against the standard basis vectors gives. Corrected all 4 comments in `60541adf`. **Lesson**: a numeric discrepancy between two computations doesn't tell you which one (if either) is "the real formula" vs. buggy — when two independently-plausible implementations disagree, check BOTH against raw ground truth before writing a conclusion into a comment, don't assume the newer/more-specific-sounding one must be structurally different rather than simply wrong.

Also independently resolved one flagged uncertainty (`Entity::ResolveBoneForwardVector`, `74618a1a`): the agent's own ground-truth check matched only 2/3 vector components and it left this open. The full ground truth (`FUN_0068A6F0.c`) is decodable once you recognize IDA split the `VTransform` struct at the wrong byte boundary in that specific decompile (4 bytes into `orient_`, not at its real 16-byte end) — `v29.orient.x`/`v29.pos.x/.y/.z` are actually `orient_.w/.x/.y/.z` in that order, not `orient_.x` plus a real position. Once corrected for that, all 3 terms match exactly.
